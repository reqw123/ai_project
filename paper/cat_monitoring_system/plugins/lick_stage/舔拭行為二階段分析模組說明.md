## 一、目的與需求背景

### 問題描述

ST-GCN 動作分類器輸出的行為標籤（如 `lick`）僅能判斷「貓咪正在舔舐」，無法進一步區分舔舐的**目標身體部位**（舔身體、舔前腳、舔後腳等）。然而在行為分析或醫學評估場景中，舔舐部位的差異具有重要意義：

- 持續舔舐特定肢體可能代表傷口、皮膚病或寄生蟲
- 舔舐頻率與分佈可作為焦慮或疼痛行為的量化指標
- 頭部朝向與接觸區域的組合判斷能過濾視角干擾造成的誤判

### 設計思路：二階段處理

```
第一階段：ST-GCN 行為分類（processors/frame_processor.py）
  ↓ 本幀已確認行為 = lick 且 confidence ≥ STGCN_BEHAVIOR_LABEL_CONFIDENCE_THRESHOLD ？
  │
  ├─ 是 → 餵入本幀真實關鍵點 (raw_kpts, kpt_conf)
  └─ 否 → 餵入 (None, None)（視同「貓不在畫面」）
        ↓
第二階段：lick_stage 精細化分析（獨立插件，逐幀呼叫 update()，但輸入內容由第一階段結果決定）
  ├── 計算耳距與身體尺度，判斷正面視角保護（front-view guard）
  ├── 若非正面視角：建立鼻部接觸梯形與身體/肢體目標區域
  ├── 測試鼻尖梯形是否與任一區域相交，取「距離最近」者為接觸區域
  ├── 推斷頭部朝向（FACING_CAMERA / FRONT_LEFT / FRONT_RIGHT / BACK_VIEW / FRONT_VIEW / NO_CAT / UNKNOWN）
  └── 輸出結構化 LickResult（含區域統計、朝向、穩定度、bout 統計）
```

> **本插件（`update()`）本身不含任何「是否為 lick」的判斷邏輯**——`LickAnalyzer.analyze()` 收到什麼就處理什麼，完全不知道、也不需要知道 ST-GCN 的分類結果。真正的「只在 lick 時才啟動」是由呼叫端 **`processors/frame_processor.py`** 決定：只有當本幀已確認的 ST-GCN 行為等於 `lick` 且信心值達到 `BehaviorTrackingConfig.STGCN_BEHAVIOR_LABEL_CONFIDENCE_THRESHOLD` 門檻時，才把本幀真實關鍵點傳給所有已註冊 plugin（包含 `LickStagePlugin` 與 `ext_body_zones/ExtBodyZonePlugin`）；其餘所有情況（`walk`/`scratch`/`shake`/`stop`/低信心/貓不在畫面）一律傳 `(None, None)`，讓 plugin 走既有的「無貓」重置路徑（`analyzer.py` 的 `_handle_no_cat()`）。
>
> 這是本模組**這次修訂前後最關鍵的行為差異**：舊版文件（含更早的版本）曾寫「本插件實際上每幀都會執行，並非只在 ST-GCN 判斷出 lick 標籤時才啟動」——這句話目前已不成立，設計選擇如下：
>
> - **不會污染統計**：`(None, None)` 對應 `zone_label="NO_TARGET"`，`LickStatistics.update()`（見 3.5）查表後直接跳過，不會把非舔舐時段的時間算進任何部位的累計時間；`models.py`（3.4）的百分比分母也只由已累計的部位時間組成，與非舔舐時段長短完全無關。`ext_body_zones/plugin.py` 的 `_run()` 在 `kpts is None` 時同樣提早 return、不寫入任何 zone 的 `time_sec`，兩個 plugin 的統計都是自我封閉的。
> - **判斷用的是即時（非顯示平滑）行為值**：`frame_processor.py` 另有一套 `_display_behavior_id`（hysteresis 平滑，只用於畫面 overlay/Node-RED 顯示防閃爍），但餵給 lick_stage 的閘門用的是未經平滑的即時 `self._last_behavior_id`/`self._last_confidence`——與 tracker/CSV/segment_logger 等其他「資料記錄」路徑共用同一份訊號，全系統判斷基準一致。
> - **代價（刻意接受）**：每次從非 lick 切回 lick，`_ema_kpts`/`_prev_trap_perp`/`_prev_trap_dir` 等跨幀平滑狀態會重置為初始值（與「貓咪離開畫面又回來」時完全相同的重置路徑），梯形方向需要重新收斂數幀才穩定；這是刻意接受的短暫視覺過渡，不代表資料錯誤。
> - 「二階段」一詞現在同時成立於兩個層次：**分析目的**的層次（粗分類 → 精細化定位）與**呼叫時機**的層次（第一階段須先確認才觸發第二階段的實際運算）。
>
> 詳細的閘門判斷式與逐行正確性驗證見 `processors/frame_processor.py` 中 `is_lick_behavior` 的計算，以及「四、資料流整合示意」。

| `models.py` | 定義 `ZoneStats`、`LickResult` 輸出結構與 JSON 序列化 | 否（純資料） |
| `statistics.py` | 累計各區域命中次數、累計時間、bout（連續舔舐段落）次數與時長 | **是** |
| `publisher.py` | 以 `ThreadPoolExecutor` 非阻塞方式 POST 結果至 Node-RED | 否（內部執行緒池，但無業務狀態） |
| `contact_regions.py` | 依鼻尖與軀幹關鍵點動態建構梯形與各目標區域，M5 起改成候選評分（見 3.7） | 否（純函式） |

| `ear_distance.py` | 計算雙耳像素距離，並以軀幹長正規化 | 否（純函式） |

| `pose_filter.py` | M4：`PoseFilter` 濾波器（confidence-aware EMA + 缺點 hold decay + 骨長品質），**尚未接線**（見 3.17） | **是** |

**未列入插件邏輯的檔案：**

- `1_自動抓取.py`：與 lick_stage 分析邏輯完全無關，是一支從 Pixabay/Pexels API 抓取貓咪行為影片供資料收集用的爬蟲腳本，僅是放置在此目錄下，並非插件架構的一部分。

**與 `ext_body_zones/` 插件的關係：** 該子目錄是**完全獨立的姊妹插件**（`ExtBodyZonePlugin`），提供另一種 7 區身體分區分類（HEAD / NECK_CHEST / SIDE_BACK / ABDOMEN / FORELIMB / HINDLIMB / TAIL），沿用同一套 17 點關鍵點順序，但擁有自己獨立的 `config.py` / `models.py` / `regions.py` / `output.py`，不呼叫、不匯入本模組的任何函式，於 `server/routes.py` 中以 `_try_register_ext_body_zone()` 單獨註冊，可獨立移除而不影響 `LickStagePlugin`。

> **兩者共用同一道 ST-GCN 閘門**：程式碼層面兩個 plugin 彼此獨立，但 `frame_processor.py` 是用同一個 `for _plugin in self._plugins: ...` 迴圈、同一個 `is_lick_behavior` 判斷結果去呼叫兩者的 `update()`（見上方「設計思路：二階段處理」）。因此雖然沒有程式碼依賴，兩者在「只在 lick 時才收到真實資料」這件事上是同步的。

## 三、各子模組詳細說明

### 3.1 `manager.py` — 對外公開介面

#### 類別：`LickStagePlugin`

系統其他元件只需與此類別互動，內部實作細節完全封裝。整合契約（見原始碼 docstring）：每個處理幀呼叫一次 `update(kpts, kpt_conf)`；`update()` 內部所有例外都會被捕捉並以 DEBUG 等級記錄，絕不會讓主系統崩潰；整個插件目錄可直接刪除而不影響主系統（`routes.py` 以 `try/except ImportError` 方式註冊）。

```python
class LickStagePlugin:
    def __init__(self, nodered_url: str = LickConfig.NODERED_URL): ...
    def update(self, kpts, kpt_conf) -> None: ...
    def draw_overlay(self, frame, frame_idx: int = 0, show: bool = True) -> None: ...
    def close(self) -> None: ...
```

| 方法 | 功能說明 |
|------|---------|
| `__init__` | 建立內部 `LickAnalyzer`；若 `nodered_url` 非空則建立 `NodeRedPublisher`，否則不推送 |
| `update(kpts, kpt_conf)` | `kpts` 為 `(17, 2)` 座標陣列（或 `None` 代表無貓），`kpt_conf` 為 `(17,)` 信心值陣列；內部呼叫 `analyzer.analyze()` 取得 `LickResult` 並（若有 publisher）發布至 Node-RED；**不回傳值、不接收 frame** |
| `draw_overlay(frame, frame_idx, show)` | 獨立的畫面疊圖方法，讀取 analyzer 上一幀快取的幾何資訊繪製到 `frame`；與 `update()` 完全解耦，可在不同時機呼叫 |
| `close()` | 關閉 `NodeRedPublisher` 的執行緒池（`wait=False`） |

> **與舊版文件的差異**：舊版描述 `__init__(config, publisher)` / `process(frame, keypoints, ...) → LickResult` / `reset()`，這些簽名在目前程式碼中均不存在。目前是 `__init__(nodered_url)` / `update(kpts, kpt_conf) → None` / `draw_overlay(...)` / `close()`。

### 3.2 `analyzer.py` — 逐幀協調器

#### 類別：`LickAnalyzer`

持有所有跨幀狀態，每幀呼叫一次 `analyze(kpts, kpt_conf, frame_idx, elapsed_sec, dt_sec) -> LickResult`。

**內部狀態（`__init__`）：**

| 屬性 | 說明 |
|------|------|
| `_stats` | `LickStatistics` 實例（並非文件舊版所稱的 `_zone_stats` 字典） |
| `_state_history` | `deque(maxlen=STATE_SMOOTH_WINDOW)`，朝向標籤歷史（用於多數決平滑） |
| `_ema_kpts` | 上一幀 EMA 平滑後的關鍵點（並非 `_prev_kps`） |
| `last_trap_pts` / `last_hit` / `last_zone_label` / `last_nose_xy` / `last_geom` / `last_nearest_label` | 供 `draw_overlay()` 讀取的上一幀 overlay 快取 |

> 沒有獨立的 `_frame_count` 屬性在 `LickAnalyzer` 上——幀計數實際上維護在 `LickStagePlugin` 內。

**實際處理流程（`analyze()` → `_handle_cat()`，非固定 12 步驟，而是含分支的流程）：**

```
analyze(kpts, kpt_conf, frame_idx, elapsed_sec, dt_sec)
  │
  ├─ 若 kpts/kpt_conf 為 None → _handle_no_cat()：記錄 NO_CAT 狀態，回傳空結果
  │     （此分支現在有兩種觸發來源，analyzer 內部無法、也不需要分辨兩者：
  │      ① YOLO 真的沒偵測到貓；② frame_processor.py 判定本幀 ST-GCN
  │      行為不是已確認的 lick，因而刻意傳入 (None, None)。兩者都應該
  │      視為「本幀不產生舔舐部位資料」，走同一條重置/NO_TARGET 路徑
  │      在語意上是正確的——見「一、設計思路：二階段處理」）
  │
  └─ _handle_cat()：
        1. EMA 平滑關鍵點（EMA_ALPHA 預設 1.0 = 不平滑，直接略過）
        2. compute_ear_distance()  → dist_px, dist_norm, valid, body_ear_ratio
        3. check_front_view_guard(kpt_conf, dist_px, body_ear_ratio) → front_guard
        4. compute_head_ear_angle() → angle_deg（供後續 user_rules 使用）
        │
        ├─ 若 front_guard=True（正臉朝鏡頭，幾何判斷不可靠）：
        │     → 直接跳過 compute_geometry / find_nearest_zone
        │     → 狀態設為 BACK_VIEW（若鼻子信心低）或 FRONT_VIEW，穩定度強制 = 1.0
        │     → zone_label = "NO_TARGET"
        │
        └─ 若 front_guard=False：
              → compute_geometry() 建立梯形與各身體目標區域
              → infer_face_state_cat_centric() 取得貓體坐標系初判狀態
              → infer_face_state_user_rules() 以角度/距離規則覆寫（優先權更高）
              → 若規則有觸發且狀態屬於 FRONT 系列，穩定度強制 = 1.0；否則呼叫 smooth_state() 多數決平滑
              → find_nearest_zone() 在所有候選區域中取「距離最近者」為接觸區域
              → 更新 overlay 快取（last_trap_pts 等）
        │
        6. self._stats.update(zone_label, dt_sec) → 委派 LickStatistics 累計
        7. 回傳 _build_result(...) 組成的 LickResult
```

> **overlay 繪製不在此流程中**：`analyzer.analyze()` 完全不觸碰畫面、不接收 `frame` 參數；繪圖是由 `LickStagePlugin.draw_overlay()` 另外呼叫 `overlay.draw_all_overlays()` 完成，讀取的是 analyzer 快取下來的上一幀幾何資訊。

### 3.3 `config.py` — 參數集中管理

#### 類別：`LickConfig`

所有閾值與幾何參數均在此定義為類別屬性（非 `dataclass`），修改時只需改這一個檔案。

**關鍵點索引（沿用專案通用的 17 點 YOLO-Pose 骨架編號，與 `utils/constants.py` 一致）：**

| 參數 | 值 | 對應部位 |
|------|----|---------|
| `KP_NOSE` | 0 | 鼻尖 |
| `KP_LEFT_EAR` | 1 | 左耳 |
| `KP_RIGHT_EAR` | 2 | 右耳 |
| `KP_CHEST` | 3 | 前胸 |
| `KP_MID_BACK` | 4 | 背部中心（標記於背部最高點，**非** chest-hip 連線中點——兩者只在脊椎打直時重合，蜷曲/拱背時會明顯偏離，這正是下方梯形彎曲自適應的量測基礎） |
| `KP_HIP` | 5 | 髖部 |
| `LIMB_SEGMENTS` | `[("FL",6,7), ("FR",8,9), ("HL",10,11), ("HR",12,13)]` | 四肢（膝關節索引, 腳掌索引） |

> lick_stage 收到的是**完整未截斷的 17 點陣列**（`frame_processor.py` 在 ST-GCN 專用的 14 點截斷處理**之前**就把原始 `kpts`/`kpt_conf` 傳給所有已註冊插件），因此這裡的索引與專案整體的 0–16 解剖對照表一致，並非誤用。

**信心值門檻：**

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `EAR_CONF_THRESHOLD` | 0.5 | 耳朵關鍵點最低信心值 |
| `NOSE_CONF_THRESHOLD` | 0.5 | 鼻子關鍵點最低信心值 |
| `LIMB_CONF_THRESHOLD` | 0.10 | 四肢關鍵點最低信心值 |
| `BODY_KP_CONF` | 0.5 | 胸部/髖部信心值門檻（計算身體尺度用） |

**頭部朝向狀態標籤（實際字串值）：**

| 常數 | 字串值 | 說明 |
|------|--------|------|
| `STATE_UNKNOWN` | `"UNKNOWN"` | 無法判斷 |
| `STATE_FRONT` | `"FACING_CAMERA"` | 正面朝向鏡頭 |
| `STATE_FRONT_LEFT` | `"FRONT_LEFT"` | 偏左的正面 |
| `STATE_FRONT_RIGHT` | `"FRONT_RIGHT"` | 偏右的正面 |
| `STATE_BACK` | `"BACK_VIEW"` | 背對鏡頭 |
| `STATE_FRONT_VIEW` | `"FRONT_VIEW"` | 前視保護觸發（暫停舔舐判定） |
| `STATE_NO_CAT` | `"NO_CAT"` | 畫面中無貓 |

> 沒有獨立的 `LEFT` / `RIGHT` / `DOWN` 狀態——「偏左/偏右」一律是 `FRONT_LEFT`/`FRONT_RIGHT`（正面朝向下的細分），也沒有低頭（`DOWN`）狀態。

**貓咪視角凝視方向門檻：**

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `CAT_FRONT_FORWARD_MIN` | 0.08 | 判定「朝前」的前向分量最小值 |
| `CAT_BACK_FORWARD_MIN` | 0.10 | 判定「背後」的前向分量最小值 |
| `CAT_LR_MARGIN` | 0.06 | 左右偏移容許誤差 |
| `CAT_LR_SIGN` | 1.0 | 左右方向符號（鏡像時可設 -1） |

**使用者規則門檻：**

| 參數 | 預設值 | 說明 |
|------|--------|------|
| `FRONT_CAMERA_ANGLE_MIN_DEG` | 45.0 | 耳鼻夾角超過此值判定為面朝鏡頭 |
| `FRONT_CAMERA_NORM_MIN` | 0.30 | 耳間距標準化值輔助門檻 |
| `BACK_CAMERA_NOSE_CONF_MAX` | 0.5 | 背對判定的鼻子信心值上限 |
| `BACK_CAMERA_DIST_MIN_PX` | 3.0 | 背對判定所需耳間距最小像素值 |
| `BACK_VIEW_REQUIRE_LOW_NOSE` | `True` | 背對判定是否要求鼻子信心值必須低於門檻 |

**正面視圖保護（front-view guard）：**

| 參數 | 預設值 | 說明 |
|------|--------|------|

**梯形彎曲自適應（2026-07-13 新增，2026-08-21 改用角度指標）：**

| 參數 | 預設值 | 說明 |
|------|--------|------|

| `CURVATURE_ANGLE_MIN_DEG` | 20.0 | `midback_angle_deg` 下限：越接近此值代表拱背/蜷曲程度越明顯（對齊該檔案的 `CANDIDATE_MIDBACK_ANGLE_LOW_THRESHOLD`） |
| `CURVATURE_BOOST_MIN` | 0.85 | 對應 `CURVATURE_ANGLE_MAX_DEG`（打直）時的梯形縮放倍率（打直時縮小） |
| `CURVATURE_BOOST_MAX` | 1.20 | 對應 `CURVATURE_ANGLE_MIN_DEG`（拱背/蜷曲）時的梯形縮放倍率（拱背時放大） |

> **問題背景**：`body_len` 是 chest-hip 兩點的**直線**距離。貓咪拱背/蜷曲理毛時，脊椎會明顯偏離這條直線，此時直線距離會低估「真實」身體尺度，導致鼻部接觸梯形在最需要精準判定的姿勢下反而系統性偏小。`midback_angle_deg`（Chest-MidBack-Hip 夾角，以 MidBack 為頂點，由 `contact_regions.py` 計算，見 3.7）就是這個彎曲程度的量測值——夾角越接近 180 度代表脊椎越直，越小代表拱背/蜷曲越明顯；`CURVATURE_*` 四個參數把它線性內插成一個縮放倍率的區間，只套用在梯形尺寸上（不影響身體橢圓/四肢區域——那些量測的是「當下真實」幾何，不該被姿態推測放大縮小）。2026-08-21 前這裡用的是 `mid_back_dist_pct`（`mid_back` 到 chest-hip 中點的正規化距離百分比）；改用角度是因為它跟 `processors/skeleton_quality_assessment.py` 的 `compute_midback_angle()` 共用同一套幾何定義（同一個物理量兩處不必各自維護一份指標），且對「彎曲程度」是更直接的量測。

### 3.7 `contact_regions.py` — 幾何計算

#### `compute_geometry(kpts, kpt_conf) -> Optional[dict]`

根據本幀鼻、胸、髖（以及可用時的雙耳）關鍵點動態建構所有接觸目標區域。若鼻/胸/髖任一信心值不足或胸髖距過小則回傳 `None`。

**回傳字典鍵值：**

```python
{
    "nose": ..., "ear_center": ...,
    "body_center": ..., "body_normal": ..., "body_axis_unit": ..., "body_len": ...,
    "midback_angle_deg": ..., "curvature_boost": ...,  # 2026-07-13 新增，2026-08-21 改用角度指標，見下方說明
    "region_rx": ..., "region_ry": ...,          # 身體橢圓半徑
    "nose_contact_trapezoid": ...,                 # (4,2) 梯形頂點（注意鍵名，非 nose_trap_pts）
    "limb_targets": [...],                          # 肢體末端圓
    "limb_strip_targets": [...],                    # 肢體條帶
    "trap_perp": ..., "trap_dir": ...,              # 未經跨幀穩定的原始方向向量，供 LickAnalyzer 平滑後重建梯形
    "trap_top_half": ..., "trap_bot_half": ..., "trap_height": ...,  # 已套用 curvature_boost 的梯形尺寸
}
```

#### `_compute_midback_angle_deg(chest, midback, hip) -> float`（2026-08-21 新增，純函式）

算 Chest-MidBack-Hip 夾角（度，MidBack 為頂點），跟 `processors/skeleton_quality_assessment.py` 的 `compute_midback_angle()` 是同一套幾何公式——這裡另外重新實作一份（不 import `processors/` 模組），維持本 plugin 低耦合、可獨立抽離的既有設計原則。任一向量長度太短（幾乎重疊）時回傳 `NaN`；信心值檢查由呼叫端（`compute_geometry()`）負責，這個函式本身不檢查。

#### `_curvature_size_boost(midback_angle_deg: float) -> float`（2026-07-13 新增，2026-08-21 改用角度指標，純函式）

依 `midback_angle_deg` 線性內插出梯形縮放倍率（區間定義見 3.3 的 `CURVATURE_*` 參數）：輸入為 `NaN`（`mid_back` 信心不足）或內插區間長度為 0 時回傳 `1.0`（不縮放，等同未量測時的既有行為）；否則依 `CURVATURE_ANGLE_MAX_DEG/MIN_DEG` 正規化並夾鉗到 `[0,1]`（角度是遞減指標，夾角越大代表越直，公式用 `CURVATURE_ANGLE_MAX_DEG - midback_angle_deg` 而非角度本身），再內插到 `[CURVATURE_BOOST_MIN, CURVATURE_BOOST_MAX]`。

`compute_geometry()` 內的計算順序：先以 `chest`/`mid_back`/`hip` 三點呼叫 `_compute_midback_angle_deg()` 算出 `midback_angle_deg`（`mid_back` 信心值需 `> EAR_CONF_THRESHOLD`，否則為 `NaN`），再呼叫 `_curvature_size_boost()` 得到 `curvature_boost`，最後把它**乘進** `trap_height`／`trap_top_half`／`trap_bot_half` 三個梯形尺寸算式——只影響鼻部接觸梯形，不影響 `region_rx`/`region_ry`（身體橢圓）或 `limb_targets`/`limb_strip_targets`（四肢區域）。

#### `find_nearest_zone(target_geom) -> Tuple[str, float, bool]`

回傳 `(zone_label, distance, hit)`，而非舊版文件所述的 `(hit, zone_label, nearest_label)`。演算法**並非固定優先順序**（肢體優先→身體→無命中），而是：

1. 蒐集所有與鼻部梯形**相交**的候選區域（身體橢圓、各肢體腳掌圓、各肢體條帶）
2. 對每個候選計算鼻尖到該區域中心線/中心的距離
3. 在所有候選中取**距離最小者**作為最終 `zone_label`
4. 若無任何候選相交，回傳 `(NO_TARGET, nan, False)`

即「距離最近者勝出」，不是「肢體圓 > 身體橢圓 > 無命中」的階層式優先權。

| 定義 | 說明 |
|------|------|
| `FrameState` | 互斥狀態常數：`NO_CAT`／`NOT_LICK`／`LOW_LICK_CONF`／`LICK_ASSIGNED`／`LICK_UNASSIGNED`。`FrameState.LICK = (LICK_ASSIGNED, LICK_UNASSIGNED)`、`FrameState.CAT_PRESENT` 是不含 `NO_CAT` 的其餘四種 |
| `ReasonCode` | `LICK_UNASSIGNED`／無效幀的原因碼：`POSE_INVALID`／`FRONT_VIEW_UNOBSERVABLE`／`NO_REGION_HIT`／`AMBIGUOUS`／`TRACK_SWITCH` |
| `AnalysisContext` | 一段 Session 的不可變 metadata（`session_id`／`video_id`／`cat_id`／`period`／`model_version`／`config_hash`／`source_fps`），由 `manager.start_session()` 建立 |
| `SourceClock` | 把來源時間戳轉成「單調遞增、跨處理速度不變」的 dt；`tick(source_timestamp)` 回傳 `(dt_sec, discontinuity, timestamp_invalid)`。相鄰時間差超過 `DEFAULT_MAX_VALID_GAP_SEC`（1.0s）視為不連續，`dt` 不累加 |
| `derive_frame_state(cat_present, is_lick, zone_assigned, *, lick_confidence=None, low_conf_threshold=None)` | 由布林條件推導 `FrameState` 的純函式 |
| `ZoneL1` / `canonical_zone(raw_label)` | 統一上層 ontology（`TORSO`／`FORELIMB`／`HINDLIMB`／`TAIL`／`UNKNOWN`），把 `lick_stage` 的 `BODY_CENTER/FL/FR/HL/HR` 映射過去 |

> **`derive_frame_state()` 跟 `LOW_LICK_CONF` 目前是「已定義但實際流程還沒觸發」**：
> `analyzer.py` 現在是直接內嵌指定 `frame_state = FrameState.LICK_ASSIGNED` 之類
> 的值，並沒有呼叫這個函式；`LOW_LICK_CONF` 需要呼叫端額外傳
> `lick_confidence`/`low_conf_threshold` 兩個參數才會被產生，但目前
> `frame_processor.py` 是在呼叫 plugin 之前就先用固定門檻
> （`STGCN_BEHAVIOR_LABEL_CONFIDENCE_THRESHOLD`）把 `is_lick` 過濾成布林值，
> 這兩個參數從未真的被傳進來過。`statistics.py`（3.5）已經準備好處理
> `LOW_LICK_CONF` 的分支、`action_gate.py`（3.14）的 CONTINUE 條件也已經把它
> 納入——但**在目前的真實管線裡，這個狀態實際上永遠不會發生，是保留給「把
> gate 邏輯搬進 plugin」這一步用的**（`derive_frame_state()` 自己的 docstring
> 也這樣寫）。這代表 `action_gate.py` 目前在真實影片上量到的效果，全部來自
> `GAP_TOLERANCE_SEC`（合併短暫的 `NOT_LICK`/`NO_CAT`），不是來自 `LOW_LICK_CONF`
> 的 hysteresis——後者已經接好、只是還沒有輸入可以觸發。

### 3.12 `event_aggregator.py` — 事件/視窗聚合（M2，2026-09-14 起委派邊界判斷給 action_gate.py）

#### 類別：`EventAggregator`

逐幀 `feed(...)`，把連續的舔毛訊號聚合成「事件」（一段 bout）跟固定長度的
「視窗摘要」（預設 60 秒，來源時間），完成時透過 callback 交給
`storage.py`（3.13）。純資料處理，不做 I/O、不匯入 numpy/cv2。

| 方法 | 功能 |
|------|------|
| `__init__(*, window_sec=60.0, period="", gap_tolerance_sec=0.0, min_bout_sec=0.0, zone_switch_min_sec=None, on_event=None, on_window=None)` | `gap_tolerance_sec`/`min_bout_sec` 預設 0.0、`zone_switch_min_sec` 預設 `None`——三者都＝完全重現 M2 舊行為（shadow）。內部建立一個 `ActionGate(gap_tolerance_sec=..., min_bout_sec=...)`；`zone_switch_min_sec` 存下來，每個 raw bout 開始時才建立對應的 `ZoneHysteresis(zone_switch_min_sec=...)`（見 3.15） |
| `feed(*, source_ts, frame_idx, dt_sec, frame_state, zone_label, action_score=None, pose_quality=None, reason_code=None, discontinuity=False)` | 每幀呼叫一次；委派 `ActionGate` 判斷 bout 時間邊界，只有 `frame_state in FrameState.LICK` 的幀才把內容（zone/動作分數）餵進當前 raw bout 的 `ZoneHysteresis`——切分器中途送出子事件時立刻回呼 `on_event`（不等 bout 整個關閉）；視窗邊界跨越時自動結算 |
| `finalize(end_source_ts=None)` | Session 結束：結算最後一段 bout（透過 `ActionGate.finalize()` + `ZoneHysteresis.flush_final()`）與最後一個未滿的視窗 |

事件 dict（`bout_aggregator._ActiveBout.to_event()`，見 3.15）欄位：
`start_source_ts`/`end_source_ts`/`duration_sec`/`start_frame`/`end_frame`/
`zone_l1`/`zone_l2`（該（子）事件累積時間最長者）/`zone_switch_count`/
`assigned_ratio`/`action_score_mean`/`action_score_min`/`pose_quality_mean`/
`unknown_reason_mode`/`raw_bout`（2026-09-14 起真的會是 `False`——`zone_switch_min_sec`
啟用且這段 bout 內部真的觸發過部位切分時；`None`/未啟用，或啟用了但這段 bout 從沒
切分過，則仍是 `True`，見 3.15）。視窗摘要 dict（`_Window.to_summary()`）欄位對應
`lick_window_summary` 資料表（見 3.13）；啟用 `zone_switch_min_sec` 後，`bout_count`/
`median_bout_sec`/`max_bout_sec` 反映切分後的子事件數，是誠實的行為改變。

### 3.14 `action_gate.py` — Bout 邊界狀態機（M6，2026-09-14 新增）

#### 類別：`ActionGate`

純狀態機，取代 `event_aggregator.py` 舊版「一遇到非 lick 幀就立刻結算」的
粗聚合。只回答「這一幀算不算某個 bout 的一部分、bout 有沒有在這一幀關閉」，
不知道 zone/geometry（那是 `bout_aggregator.py` 的工作，見 3.15）。

| 方法 | 功能 |
|------|------|
| `__init__(*, gap_tolerance_sec=None, min_bout_sec=None)` | 省略時吃 `config.py` 的 `GAP_TOLERANCE_SEC`/`MIN_BOUT_SEC`（各 0.5s 粗略預設值，環境變數可覆寫） |
| `feed(*, ts, frame_idx, dt, frame_state, discontinuity=False)` | 回傳 `(in_bout, closed_bout)`；`closed_bout` 非 `None` 代表這一幀讓一個 bout 真正關閉且通過 `min_bout_sec` 過濾 |
| `finalize()` | Session 結束：強制關閉仍開著的 bout（一樣過 `min_bout_sec` 過濾） |
| `is_open` | 目前是否身處一個 bout 內（含寬限期中） |

**START/CONTINUE 不是兩個 `lick_confidence` 數值門檻，是兩組寬鬆度不同的
`FrameState` 集合**（`lick_confidence` 在 `is_lick=False` 時語意上不是
「P(lick)」，見 3.11 的說明；拿它開新門檻會製造第二套跟 M1
`low_conf_threshold` 不同步的信心判準）：

- **START**（開啟新 bout）：`frame_state ∈ FrameState.LICK`——跟 M2 原本開始
  一個 bout 的條件一致。
- **CONTINUE**（維持已開啟的 bout）：上面那組 **+ `LOW_LICK_CONF`**——但如
  3.11 所說，這個狀態目前實際流程不會出現，所以 CONTINUE 現階段等同 START，
  差別要等 `LOW_LICK_CONF` 真的被觸發才會顯現。

再疊兩層時間容忍：`GAP_TOLERANCE_SEC`（CONTINUE 都不滿足時的寬限期，超過
才真正關閉；寬限期本身不計入回報的舔毛時長）跟 `MIN_BOUT_SEC`（bout 太短
直接丟棄，不產生事件）。`discontinuity=True`（來源時間不連續）視同寬限期
立刻用盡，強制關閉，不受 `gap_tolerance_sec` 保護。

### 3.15 `bout_aggregator.py` — Bout 內部部位邊界狀態機（M6，2026-09-14 第二部分新增）

#### 類別：`ZoneHysteresis`（+ 內容累加器 `_ActiveBout`，從 `event_aggregator.py` 移過來）

`action_gate.py`（3.14）決定 bout 的**時間**邊界（有沒有在舔）；這裡決定同一段
時間邊界**內部**的**部位**邊界（舔的是哪裡）——貓咪真的持續換部位時該切成子
事件，但候選評分（3.7）在相鄰 zone 間偶爾抖動、或短暫幾幀 `NO_REGION_HIT`
不該被當成真的換部位。跟 `action_gate.py` 同一種 hysteresis 精神，維度不同
（時間 vs 部位），刻意分成兩個檔案。

設計是「候選 streak」：收到跟目前已確認 zone 不同的候選 zone 時先不採信，
候選累積夠久（`zone_switch_min_sec`）才確認真的換了部位；累積不夠又跳回原
zone 就當抖動吸收，streak 歸零。確認切換時，新子事件的起點是「確認的這一
幀」，不回溯到候選開始的那一幀——刻意簡化，避免另外維護逐幀緩衝/復原機制，
代價是換部位的時間戳最多有 `zone_switch_min_sec` 的滯後。

| 方法 | 功能 |
|------|------|
| `__init__(*, zone_switch_min_sec=None)` | `None`＝完全不啟用（shadow，`_active` 貫穿整個 bout 不切分）；非 `None` 才啟用候選 streak 判斷 |
| `feed(ts, frame_idx, dt, l1, l2, action_score, pose_quality, reason_code, assigned)` | 只在 `event_aggregator.feed()` 判定 `frame_state in FrameState.LICK` 時才會被呼叫；回傳非 `None` 代表候選 streak 撐夠久、真正觸發部位切分，內容是剛結算的子事件（`raw_bout=False`） |
| `flush_final()` | bout 真正關閉（或 session 結束）時呼叫：結算最後一段內容；這個 bout 全程從沒觸發過切分才是 `raw_bout=True`，觸發過的話連最後一段也誠實標 `False` |

**為什麼 `zone_switch_min_sec` 不比照 `gap_tolerance_sec`/`min_bout_sec` 用
`0.0` 當關閉哨兵**：`0.0` 對時間類參數（寬限期/最短長度）本身是合法邊界
（沒有寬限、沒有最短限制，仍是完整定義的行為）；但 `zone_switch_min_sec=0.0`
語意上是「任何一幀不同 zone 就切」——完全不同、更激進的合法行為，不能借代
「關閉」。所以改用 `None` 當唯一的「未啟用」哨兵。

**呼叫端注意事項**：`min_bout_sec` 是在整個 raw bout 真正關閉時才判斷，但
zone 切分可能在 bout 仍開著、遠早於關閉前就已經送出子事件。若 `min_bout_sec`
設得比 `zone_switch_min_sec` 大很多，理論上可能出現「已經送出的子事件，事後
發現整個 raw bout 被 min_bout 丟棄」的邊界情形——不做跨模組交易式回滾。目前
預設值 `MIN_BOUT_SEC=0.5s` ≤ `ZONE_SWITCH_MIN_SEC=1.0s`，不會觸發。

**真實影片驗證的陰性結果**：3 支「白貓舔舐測試」影片（見「真實影片驗證現況」）
全程 `zone_l1` 都停在同一個部位沒有真正持續切換過，`bout_aggregator.py` 因此
沒有東西可切、事件數/coverage 跟只有 `action_gate.py` 生效時完全一樣——這是
符合預期的結果（這 3 支影片本來就是同一段持續舔同一隻前腳的鏡頭），不是沒
接上；合成資料的 `test_bout_aggregator_unit.py` 已涵蓋切分路徑本身的正確性。

### 3.17 `pose_filter.py` — 共用姿態濾波器（M4 第一階段，2026-09-14 新增，尚未接線）

#### 類別：`PoseFilter`

逐幀 `update(kpts, kpt_conf, ...)` → `PoseFrame`（見 3.16）。取代/擴充
`analyzer.py` 現有的樸素關鍵點 EMA（`self._ema_kpts`，`config.py` 的
`EMA_ALPHA`），目標是讓 `lick_stage`／`ext_body_zones` 兩個外掛未來能吃
同一份平滑後的關鍵點，而不是各自（可能不一致地）處理。

| 方法 | 功能 |
|------|------|
| `__init__(*, alpha=1.0, min_conf=None, hold_decay_frames=0, decay_alpha=0.05, bone_pairs=None, bone_len_ema_alpha=0.05)` | `alpha>=1.0`＝完全不平滑（沿用 `EMA_ALPHA` 既有慣例）；`min_conf`/`bone_pairs` 未給則對應功能不啟用 |
| `update(kpts, kpt_conf, *, frame_idx=0, source_timestamp=None)` | 回傳 `PoseFrame`；整幀缺失（任一為 `None`）回傳全 `None` 的 `PoseFrame`，**不改動內部平滑狀態** |
| `reset()` | 清空跨幀平滑狀態（新 track/session 時呼叫，政策由呼叫端決定，見下方） |

**三個功能各自獨立、按需啟用**（完整理由見 `pose_filter.py` 開頭 docstring）：

1. **confidence-aware EMA**（一律生效，`alpha<1.0` 時）：`effective_alpha_i
   = alpha * clamp(conf_i, 0, 1)`——信心低的點平滑後幾乎不動；`NaN` 信心透過
   同一條公式自然歸零，不需要另開分支。`min_conf`/`bone_pairs` 全不給、
   信心值全是 1.0 時，數值上跟 `analyzer.py` 現有的樸素 EMA 逐幀完全等價。
2. **缺點 hold decay**（只有給 `min_conf` 才啟用）：低於門檻的讀數凍結在
   目前平滑值（`effective_alpha=0`），連續超過 `hold_decay_frames` 幀才用
   很小的 `decay_alpha` 緩慢拉回，避免永久卡死在舊位置。
3. **骨長品質**（只有給 `bone_pairs` 才啟用）：對每對骨骼端點追蹤一份獨立、
   更慢的預期骨長 EMA（`bone_len_ema_alpha`，刻意跟位置平滑分開），換算
   相對偏差成 `[0,1]` 品質分數；第一幀（尚無預期值可比較）回傳 `None`
   （「尚不可得」，不是「品質為 0」）。

**`update(None, None)` 不改動任何內部平滑狀態**：刻意跟 `analyzer.py` 現在
「每個非 lick 幀都呼叫 `_reset_transient_state()` 清空 `_ema_kpts`」的政策
分開——那是 `analyzer.py` 自己的選擇，不是這個共用模組該內建的假設；要沿用
那個政策，呼叫端在對應時機自行呼叫 `reset()` 即可。

**尚未接線**：`event_aggregator.py`/`analyzer.py` 裡 `pose_quality=None
# M4 由共用 PoseFrame 提供` 這個既有佔位註解就是等這裡接上——接線工作要動到
`frame_processor.py`（全系統共用核心檔案），是獨立、需要另外確認的下一步
（見「下次開始」章節），這次只完成模組本身。

## 五、梯形接觸區域設計說明

### 為什麼使用梯形（而非圓形或矩形）？

貓咪舔舐時，鼻尖到接觸點的距離並非固定，會隨頸部伸展而變化。梯形設計的優點：

- **方向性**：梯形沿鼻→體中心方向延伸，自然對齊貓咪的舔舐方向
- **漸寬設計**：靠近鼻尖端較窄（`NOSE_TRAP_TOP_W_RATIO=0.10`），遠端較寬（`NOSE_TRAP_BOT_W_RATIO=0.20`），容許舔舐目標的位置誤差隨距離增加
- **動態跟隨**：每幀根據當前關節位置重建，自動適應體型與姿勢變化

### 接觸區域判定邏輯（並非固定優先順序）

`find_nearest_zone()` 會蒐集鼻部梯形與**所有**候選區域（身體橢圓、四個肢體腳掌圓、四個肢體條帶）中「有相交」的項目，再從中選出**鼻尖距離最近**的一個作為最終接觸區域；若都沒有相交則回傳 `NO_TARGET`。因此不存在「肢體圓一定優先於身體橢圓」的階層規則——只是實務上肢體圓通常較小、較貼近鼻尖，距離自然容易勝出。
