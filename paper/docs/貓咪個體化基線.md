## 〇、現況（2026-09-04）：Python 端個體化基線引擎（`analytics/`）

> 📖 **一句話摘要**：基線計算／偏差評分／跨類別融合三段邏輯已從 Node-RED function node 移植成獨立 Python 模組，改用「連續時長」與「稀疏次數」兩種不同統計模型，並改用 Python 端自己的 SQLite 儲存多天歷史，不再與 Node-RED 共用同一份 `global.json`。

### 0.1 架構總覽

```
BehaviorTracker（每日累積）──跨日──▶ daily_store.save_day() ──▶ SQLite: daily_history
                                                                     │
   觸發者 A：dashboard/refresher.py 背景執行緒（約每 2 秒，_cache_is_fresh 去重）
   觸發者 B：Node-RED analytics_deviation_bridge.json → POST /api/deviation（新舊引擎比對用）
                                                                     │
                     baseline.compute_baseline(history, min_days=7, max_days=30, excluded_dates)
                       ├─ 連續指標（walk/stop/lick/scratch _time）：mean/std/median/MAD/EWMA
                       └─ 稀疏計數（walk/stop/lick/scratch/shake _count）：保留每日原始序列
                                                                     │
                     deviation.compute_deviation(today, baseline)
                       ├─ 連續 → 穩健 z-score = (today − median) / (MAD × 1.4826)
                       └─ 計數 → Poisson（過度離散時退回 Negative-Binomial）尾機率 → sigma_equivalent
                                                                     │
                     fusion.compute_fusion(deviation, class_c_score)
                       Class A（lick/scratch 時長+次數，權重和 0.85）× 45%   ← 可單獨觸發等級 override
                       Class B（shake/walk/stop）                    × 25%
                       Class C（節律／轉移，外部傳入，本模組不計算）    × 30%
                       → score 0–100 → Normal(<20) / Mild(<45) / Moderate(<70) / Severe(≥70)
                                                                     │
                     dashboard/cache.set_latest() → GET /api/deviation/latest → /dashboard/baseline
```

> ⚠ 融合權重與 sigma 門檻（2.5 / 3.0 / 4.0）為專家經驗值，**無資料驅動校準**——`analytics/config.py`、`analytics/fusion.py` 原始碼逐項標註證據等級（【文獻支持】／【與 Node-RED 原版數值一致】／【工程慣例，無直接文獻依據】／【數值穩定用途】），論文中應誠實列為限制。完整文獻清單見 `paper/docs/個體化基線與異常偵測文獻來源.md`。

### 0.2 模組與職責

| 模組 | 職責 |
|---|---|
| `analytics/daily_store.py` | Python 端**獨立**的多天歷史持久化（SQLite，`LoggingConfig.DAILY_HISTORY_DB_PATH`，預設 `paper/baseline_data/daily_history.db`）。不讀、不寫 Node-RED 的 `global.json`／任何 Node-RED context——資料來源是 `trackers/behavior_tracker.py` 自己每天累積的 `get_today_stats()`。 |
| `analytics/baseline.py` | `compute_baseline()`：把多天 `DailyRecord` 歷史，依「監測時數是否達標」「是否被手動排除」「最近 N 天」三層過濾後，算出每個指標的 mean/std/median/q1/q3/iqr/mad/ewma/rolling_std。 |
| `analytics/deviation.py` | `compute_deviation()`：把「今日值」對照基線，依指標類型選穩健 z-score 或 Poisson/NB 尾機率兩種模型之一。 |
| `analytics/fusion.py` | `compute_fusion()`：把偏差結果依 Class A/B/C 加權融合成單一 0–100 風險分數與等級。 |
| `analytics/config.py` | 上述模組所有可調參數集中管理，**每個常數都標註文獻依據等級**（見上方 ⚠ 說明），獨立於主專案 `config.py`（比照 `plugins/lick_stage/config.py` 的既有模式）。 |

### 0.3 `DailyRecord`（每日彙整資料結構）

`analytics/baseline.py` 定義的每日歷史紀錄欄位（等同 Node-RED `v2_daily_history` 陣列裡的一筆）：

```
day, monitoring_seconds,
walk_time, walk_count, stop_time, stop_count,
lick_time, lick_count, scratch_time, scratch_count,
shake_count, active_time, rest_time
```

> 💡 沒有 `shake_time`——甩頭只計次數不計時長（`shake_count` 屬於稀疏計數指標，見下方 0.4）。

### 0.4 為什麼分兩種統計模型（連續 vs. 稀疏計數）

這是這次移植相對 Node-RED 舊引擎**唯一的實質行為變化**（其餘公式刻意保持數值一致，見下方各節）：

- **連續時長指標**（`CONTINUOUS_METRICS`：`walk_time` / `stop_time` / `lick_time` / `scratch_time`）：用**中位數絕對離差（MAD）**做穩健 z-score，`z = (today − median) / (MAD × 1.4826)`。MAD 有 50% 崩潰點（std 是 0%），基線視窗裡一兩天異常長的理毛時間不會把「正常範圍」的估計拉歪。
- **稀疏事件計數指標**（`COUNT_METRICS`：`walk_count` / `stop_count` / `lick_count` / `scratch_count` / `shake_count`）：改用**Poisson（或過度離散時 Negative-Binomial）尾機率**，問「如果這隻貓真實的每日發生率是基線估出來的樣子，今天觀察到至少這麼多次，有多意外？」而不是算 z-score——健康貓 `scratch_count` 這類值常態下多天是 0/1，std 很小，舊版單純 `z=(today-mean)/std` 容易讓「多抓一次」就衝破門檻；Poisson/NB 尾機率能給出誠實的機率而不需要非退化的 std。
- 兩種模型最終都會換算成同一個 `sigma_equivalent`（Poisson/NB 路徑是「同尾機率的常態 z 值」），下游 `fusion.py` 因此不用管某個指標是哪種模型算出來的，統一用同一組 σ 門檻（2.5/3.0/4.0）判讀。

### 0.5 關鍵參數（`analytics/config.py` 現值）

| 參數 | 值 | 依據等級（原始碼標註） |
|---|---|---|
| `EWMA_ALPHA` | 0.15 | 與 Node-RED 原版數值一致（刻意不變，避免搬遷後基線突變） |
| `MIN_BASELINE_DAYS`（預設） | 7 天 | 與 Node-RED 原版一致 |
| `MAX_BASELINE_DAYS`（預設） | 30 天 | 工程慣例，無直接文獻依據 |
| `MIN_DAILY_MONITORING_SEC` | 3600 秒（1 小時） | 工程慣例，無直接文獻依據 |
| `MAD_SCALE`（穩健 z-score 換算常數） | 1.4826 | 文獻支持（Iglewicz & Hoaglin, 1993） |
| `COUNT_OVERDISPERSION_RATIO`（Poisson→NB 切換門檻） | variance/mean ≥ 1.5 | 方向有文獻支持，具體切點為工程選擇 |
| `LICK_SANITY_UPPER/LOWER_SEC`（群體參考值檢查） | 6 小時／0.5 小時 | 文獻支持（Eckstein & Hart, 2000） |
| `SCRATCH_SANITY_UPPER_SEC` | 10 分鐘 | 文獻支持（Eckstein & Hart, 2000） |

基線信心等級（`_confidence_for`）：`< 7` 天 = Low、`< 30` 天 = Medium、`≥ 30` 天 = High。

### 0.6 Class A/B/C 融合（`fusion.py`）

| Class | 特徵 | 權重 |
|---|---|---|
| A（自我照護行為，總權重 45%） | `lick_time` 0.30、`lick_count` 0.15、`scratch_time` 0.30、`scratch_count` 0.10（合計 0.85，內部再正規化） | 0.45 |
| B（一般活動，總權重 25%） | `shake_count` 0.40、`walk_time` 0.30、`stop_time` 0.30 | 0.25 |
| C（節律／轉移；由呼叫端算好傳入，本模組不計算） | — | 0.30 |

**Class A override 規則**：若 Class A 任一指標的 `|sigma_equivalent|` 達到 2.5 / 3.0 / 4.0，即使加權總分較低，最終等級也會被拉高到對應的 Mild / Moderate / Severe（單一自我照護行為異常可以獨立觸發告警，不會被其他正常指標的加權平均稀釋掉）。

**風險等級（0–100 分）**：`Normal (<20)` / `Mild Behavioral Deviation (<45)` / `Moderate Behavioral Deviation (<70)` / `Severe Behavioral Deviation (≥70)`。

> ⚠ **與舊 Node-RED 引擎的差異，容易搞混**：數值門檻（20/45/70）刻意跟舊引擎一致，但**等級名稱不同**——舊引擎是 Normal / Attention / Warning / High Risk（見下方第二節「健康預警引擎」），新引擎是 Normal / Mild / Moderate / Severe Behavioral Deviation。兩套系統目前並存（見 0.8 節），對照時不要假設名稱可以互換。

> ⚠ Class A/B/C 三個權重（45/25/30）與 `shake_count` 在 Class B 內的權重（0.40，三者中最高）皆為專家經驗值：`fusion.py` 原始碼註解明確指出，一次針對性文獻檢索（2026-08）**沒有**找到支持「自我照護行為比一般活動更具疾病特異性」這個隱含假設的直接證據（Lopes et al., 2021；Merck Veterinary Manual 均把兩者視為同一組 sickness behavior 的共現症狀，而非特異性層級關係）；`shake_count` 權重最高也沒有文獻支持頭部甩動頻率與耳疾診斷的量化關聯（Brame & Cain, 2021 僅指出敏感但非特異）。這些是誠實揭露的限制，不是待修的 bug，但論文方法論章節應如實說明。

### 0.7 資料持久化：獨立於 Node-RED 的 SQLite

`analytics/daily_store.py` 刻意**不共用** Node-RED 的 `global.json`（`NodeRedConfig.GLOBAL_CONTEXT_PATH`），改用 Python 端自己的 SQLite（`LoggingConfig.DAILY_HISTORY_DB_PATH`，預設 `paper/baseline_data/daily_history.db`），資料來源是 `BehaviorTracker.check_daily_reset()` 掛的持久化 hook，跟 Node-RED 完全獨立收集。

- **動機**：過去 Python 端基線比對是直接轉發 Node-RED 那份 `v2_daily_history`，兩邊共用同一個資料源——2026-08-09 曾發生假資料測試蓋掉 `v2_daily_history` 7 天份紀錄且無法復原的事故，兩邊會一起壞掉、比對也看不出異狀。獨立收集後，兩邊資料源分岔即代表其中一邊有問題，等於多一層資料完整性檢查。
- **已知取捨**：兩邊跨日觸發時機不完全相同（Node-RED 靠 inject 準時 00:00 觸發；Python 是下一次有 frame 進來時才觸發，不受 Node-RED 停機影響但時間點可能差幾分鐘），比對時應留容許誤差。

### Tab 2：第2層 行為分析引擎

資料從分析引擎入口流入，依序經過 4 個計算節點再輸出至各 UI 面板。

#### 計算流水線

```
行為分布計算 → 行為節律分析 → 偏差分析引擎 → 健康預警引擎
```

**① 行為分布計算**
- 計算 5 種行為各佔總時間的百分比
- 輸出 `distribution` 物件

**② 行為節律分析**
- 將 24h 分成 4 個時段：`00-06 / 06-12 / 12-18 / 18-24`
- 計算各時段的主導行為（dominant）及各行為佔比
- 輸出 `rhythm` 物件

**③ 偏差分析引擎**
- 與 `v2_baseline`（個體化基線）比較
- 計算各指標相對於基線 mean 的百分比偏差及 σ 值
- 無基線時 `deviation_available = false`

**④ 健康預警引擎**（核心）

風險分公式：

```
riskScore = dScore×30% + fScore×35% + rScore×20% + tScore×15%
```

| 分量 | 說明 | 不需基線 |
|------|------|----------|
| **dScore**（行為占比偏離，0~100） | 今日各行為比例是否超過固定門檻 | ✅ |
| **fScore**（行為頻率偏離，0~100） | 與個體基線相比各行為是否異常偏高 | ❌ 需基線 |
| **rScore**（行為節律偏離，0~100） | 深夜搔抓/甩頭、白天活動量不足 | ✅ |
| **tScore**（行為轉移偏離，0~100） | lick↔scratch 循環、shake→shake 連續 | ✅ |

風險等級分界：

| 分數 | 等級 | 顏色 |
|------|------|------|
| 0~19 | Normal | 綠 |
| 20~44 | Attention | 橘黃 |
| 45~69 | Warning | 橘紅 |
| 70~100 | High Risk | 紅 |

**預設行為門檻**（可在飼主設定調整）：

| 設定 | 預設 |
|------|------|
| 舔舐占比上限 | 20% |
| 搔抓占比上限 | 15% |
| 甩頭占比上限 | 10% |
| 靜止占比上限 | 55% |
| lick↔scratch 警戒次數 | 10 次 |

| `save_event_tag` | 寫入 `v2_event_tags`（file store），同一天 upsert |
| `toggle_exclude_date` | 切換 `v2_excluded_dates` 排除清單，立即觸發基線重算 |
| `test_discord` | 發送測試訊息到 Discord Webhook |

**Output 1** → 觸發基線重算
**Output 2** → Discord HTTP Request

---

#### Discord 風險通知

- 只在 `健康預警引擎` output 2（需通知）才觸發
- dedup key = `risk.level + '|' + alerts 類型串`，同樣的警報不重複推播
- 通知靈敏度（`notify_level`）由飼主設定控制：

| 等級 | 觸發條件 |
|------|----------|
| 1（低） | High Risk（分數 ≥ 70）才推播 |
| 2（中，預設） | Warning 以上（分數 ≥ 45）推播 |
| 3（高） | Attention 以上（分數 ≥ 20）即推播 |

---

### Tab 3：第3層 基線引擎

**個體化基線計算器**（`66a22e0ec663d07d`）

篩選邏輯（三層過濾）：

```
v2_daily_history
   ↓ 層1：monitoring_seconds >= MIN_DAILY_SEC (3600 秒)
   ↓ 層2：手動排除（v2_excluded_dates）
   ↓ 層3：取最近 30 天
   ↓ 計算 mean / std / median
→ 寫入 v2_baseline（file store）
```

| 設定 | 說明 | 預設 |
|------|------|------|
| `MIN_BASELINE_DAYS` | 從 `v2_user_settings.baseline_days` 讀取 | 7 天 |
| `MIN_DAILY_SEC` | 每天最少監控秒數 | 3600（1小時） |
| `REQUIRED_PERIODS` | 限定哪些時段必須有資料 | `[]`（不限） |

基線指標（各指標均計算 mean / std / median）：

`lick_count / lick_time / scratch_count / scratch_time / shake_count / shake_time / walk_count / walk_time / stop_time / stop_count`

### Tab 4：定時任務

| 節點 | 觸發時機 | 說明 |
|------|----------|------|
| 每日午夜觸發 | 00:00 每天 | 觸發「每日統計彙整」 |
| 每小時快照 | 每 3600 秒 | 輸出偏差快照至 `deviation_log.csv` |
| 系統啟動檢查 | 啟動後 2 秒 | 偵測跨日並清除舊的 `v2_today` |
| 手動觸發基線計算 | 手動 | 直接觸發基線計算器 |
| 手動觸發每日彙整 | 手動 | 手動將今日資料存入歷史 |
| 手動觸發全部重置 | 手動 | 清除所有 v2_today / v2_hourly / v2_matrix |

**每日統計彙整**（`c5ce881398ee6376`）：
- 從 `v2_today` 讀取累積資料
- 計算 4 個時段的行為分布（`periods`）
- 同一天 upsert 去重後 push 進 `v2_daily_history`（最多保留 90 天）
- 若 `monitoring_seconds < 1800` 秒則跳過記錄
- 重置 `v2_today` 為新一天的空資料
