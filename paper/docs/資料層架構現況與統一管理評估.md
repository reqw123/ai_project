## 二、資料層：精確的現況分界線

### 已經在 Python 端

- **今日逐行為即時累積**：`trackers/behavior_tracker.py` 的 `get_today_stats()`。每個行為的次數／時長、`hourly_distribution`、`transition_matrix`、`low_conf`、`not_detected_time`、`monitoring_seconds`、`cat_visible_time`、`total_uptime`、`behavior_min_duration`／`behavior_max_duration` 全部在這裡即時算好，回傳一個 Python `dict`（見第三節資料結構）。
- **送給 Node-RED 的資料，Node-RED 沒有重算**：`processors/frame_processor.py`（約第 719～722 行）組推論結果 payload 時，直接把 `tracker.get_today_stats()` 的結果放進 `today_stats` 欄位送出。Node-RED 的「數據分發器」拿到後只是把 `data.today_stats` 存一份鏡像（`global.v2_today`），自己不重新計算。
- **`C:\a\tracker_state.json`**：Python 端持久化落地檔（`behavior_tracker.py` 內部 `json.dump` 寫的）。Node-RED 自己的「事件時間軸引擎」在註解裡明確承認這是「authoritative daily totals」，優先讀取這個檔案而非自己的 context。
- **`analytics/` 套件 + `/api/deviation`**：基線統計／偏差評分／證據融合這整套計算邏輯已 100% 是 Python（`baseline.py`／`deviation.py`／`fusion.py`），詳見 `analytics/README.md`。目前只透過 `analytics_deviation_bridge.json` 被動呼叫比對，尚未成為 `cat_health_v3_flow.json` 的正式資料來源。

### 還在 Node-RED 端（待遷移的部分）

- **`global.v2_today`**：Python 送來的 `today_stats` 鏡像。本身不是 Node-RED 算的，但「這份鏡像何時該被信任、會不會被覆蓋」完全是 Node-RED 在管——2026-08-09 的假資料測試曾直接寫壞這個 key，事後靠即時資料流自動覆蓋回真實值才復原（見下方「相關事故紀錄」）。
- **`global.v2_daily_history`（多天滾動歷史，基線真正的輸入）**：由 Node-RED 的「每日統計彙整」JS function 在午夜觸發（或手動觸發）時，讀它自己的 `v2_today` 鏡像組一筆新紀錄 append 進去，同時寫一份 `C:\a\daily_history.csv`。**「把今日彙整成一天、累積成多天視窗」這整段邏輯完全不在 Python**，是資料層裡最值得優先遷移的部分——因為它是基線計算唯一的輸入來源，而且目前的儲存機制（Node-RED file-context store，見下方「已知風險」）相當脆弱。
- **`C:\a\noda_data.csv`**：每 5 分鐘一筆的細粒度紀錄，由 `貓咪主控.json` 的「建立CSV→儲存CSV」file node 寫的，不是 Python。
- **資料管理動作**：排除某天（`v2_excluded_dates`）、刪除某天紀錄、事件標記（`v2_event_tags`）、飼主設定（`v2_user_settings`）——全部只存在 Node-RED global context，Python 端完全不知道這些東西存在。`/api/deviation` 呼叫時是靠 `analytics_deviation_bridge.json` 的橋接節點把這些資料組進請求 body 才傳得過去（見 `組成 /api/deviation 請求` function node）。

## 四、`global.json`（Node-RED context store）的內容分類

`C:\Users\homec\.node-red\context\global\global.json` 是 Node-RED 的共用狀態儲存區，**不是單一性質的「統計完的結果」**，實際內容混合四種不同來源：

| 類型 | 例子 | 誰算的 |
|---|---|---|
| Python 已算好的資料鏡像 | `v2_today` | Python（`today_stats`）算好送過來，Node-RED 只存一份，沒有重算 |
| Node-RED 自己算的統計結果（舊引擎） | `v2_daily_history`、`v2_baseline`、`v2_deviation`、`v2_risk` | Node-RED 自己的 JS function 算的，Python 完全沒參與 |
| Python 算好、寫回來比對用的結果 | `v2_baseline_py`、`v2_risk_py`、`v2_deviation_py` | Python 透過 `/api/deviation` 橋接算的，寫回來只為了跟上一列對照，不影響正式判斷 |
| 純設定／狀態，不是統計結果 | `python_ip`、`v2_excluded_dates`、`v2_user_settings`、`v2_event_tags` | 都不是，是設定值或旗標 |

**已知風險**：全部變數共用同一個檔案、同一個 `global.set(key, value, 'file')` 機制，沒有 schema、沒有交易安全。2026-08-09 曾因測試用的假資料節點直接寫入正式 key，覆蓋掉 `v2_daily_history` 裡 2026-08-02～08-08 共 7 天的真實資料，且找不到任何備份／原始紀錄可以復原（`noda_data.csv` 剛好在同一段期間有 3 週的記錄空窗）。這是本文件把 `v2_daily_history` 列為優先遷移目標的直接原因。

**為什麼這個檔案叫 `global.json`、路徑是這裡**：`C:\Users\homec\.node-red\settings.js` 第 357~364 行的 `contextStorage` 設定：

```js
contextStorage: {
    default: { module: "memory" },
    file: { module: "localfilesystem" }
}
```

`default` 用 `memory`（純記憶體，不落地），`file` 用 Node-RED 內建的 `localfilesystem` 模組（真正寫到磁碟）——這正是為什麼所有 `global.get/set(key, value, 'file')` 呼叫都一定要帶那個 `'file'` 參數，漏了就會落到 `default`（memory），讀寫變成兩個互不相干的儲存空間（`python_ip`、`v2_today` 曾經因此各自出過一次 bug，已修復）。`global.json` 這個檔名跟 `context/global/` 這個路徑結構，是 `localfilesystem` 模組對每個 context scope 的內建命名慣例，不是專案裡任何設定指定的，模組本身也沒有提供自訂檔名的選項——只能透過 `contextStorage.file.config.dir` 改資料夾位置，檔名仍會是 `global.json`。

## 五、若要「統一由 Python 端管理」——三層各自的評估

- **資料層**：投資報酬率最高、風險最低。今日即時資料已經是 Python 在算，缺的只是把「多天歷史滾動」也搬進 Python（自己的持久化檔案，例如 SQLite 或結構化 CSV，取代 Node-RED 的 `v2_daily_history`），順便解決共用 context 檔案的資料安全問題。
- **分析層**：`analytics/` 套件已經是現成的分析層，缺的是（1）正式讓 `cat_health_v3_flow.json` 呼叫 `/api/deviation` 取代自己的 JS 計算（ADR 0001 §2 排定但尚未執行），（2）把 Class C（節律／轉移分析）也搬進 Python——目前這塊仍留在 Node-RED，是 `analytics/README.md`「還沒做的事」列出的項目。
- **監測層**：投資最大的一塊。現在的「個體基線面板」是 Node-RED Dashboard 的 AngularJS 樣板（`ui_template` 節點），連按鈕動作（排除此天、刪除紀錄、存設定）都是靠 `scope.send()` 送回 Node-RED flow 處理，並透過 Node-RED Dashboard 的 websocket 機制即時推送更新（見「排除此天即時更新」的追蹤結果，2026-08-09 討論）。要換成 Python 端管理，等於要重寫一個網頁前端並重做即時推送機制，不是把邏輯搬過去而已。

**初步建議（未定案）**：資料層＋分析層值得做，監測層先不要動——讓 Node-RED Dashboard 降級成「純顯示層」，定期打 Python API 拿資料顯示，不自己算東西。這樣可以拿到「單一事實來源」的好處，又不用花大把時間重造一個網頁前端。

## 七、2026-08-09 決定：暫緩搬遷／重新命名 `global.json`

原本討論要把 `global.json` 搬到新位置並重新命名，讓新舊引擎都指向同一份檔案。評估後發現：Node-RED 內建 `localfilesystem` 模組的檔名（`global.json`）無法透過設定自訂，真要「重新命名」必須讓相關 function node 改用 `fs` 模組直接讀寫全新的共用檔案，工程量牽涉 `貓咪主控.json`／`cat_health_v3_flow.json` 好幾個 function node，跟第六節「資料層」待辦本質是同一件事。

**決定**：暫緩搬遷與重新命名，先只把現有路徑記錄下來，供 Python 端日後需要直接讀取這份資料時使用：

- `paper/config.py`：`NodeRedConfig.GLOBAL_CONTEXT_PATH`（第 481 行 `NodeRedConfig` class 內），預設值 `C:\Users\homec\.node-red\context\global\global.json`，可用環境變數 `CAT_MONITORING_NODERED_GLOBAL_CONTEXT_PATH` 覆寫。
- 目前**只記錄路徑，沒有任何程式碼讀取或解析**這個檔案——之後要做的話，需要一個轉接層把 `v2_daily_history` 的欄位（見第二節）轉成 `analytics.baseline.DailyRecord`，這是第六節「資料層」待辦成真時要做的事，不是現在。
