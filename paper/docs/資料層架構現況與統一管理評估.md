## 四、`global.json`（Node-RED context store）的內容分類

`C:\Users\homec\.node-red\context\global\global.json` 是 Node-RED 的共用狀態儲存區，**不是單一性質的「統計完的結果」**，實際內容混合四種不同來源：

| 類型 | 例子 | 誰算的 |
|---|---|---|
| Python 已算好的資料鏡像 | `v2_today` | Python（`today_stats`）算好送過來，Node-RED 只存一份，沒有重算 |
| Node-RED 自己算的統計結果（舊引擎） | `v2_daily_history`、`v2_baseline`、`v2_deviation`、`v2_risk` | Node-RED 自己的 JS function 算的，Python 完全沒參與 |
| Python 算好、寫回來比對用的結果 | `v2_baseline_py`、`v2_risk_py`、`v2_deviation_py` | Python 透過 `/api/deviation` 橋接算的，寫回來只為了跟上一列對照，不影響正式判斷 |
| 純設定／狀態，不是統計結果 | `python_ip`、`v2_excluded_dates`、`v2_user_settings`、`v2_event_tags` | 都不是，是設定值或旗標 |

**已知風險**：全部變數共用同一個檔案、同一個 `global.set(key, value, 'file')` 機制，沒有 schema、沒有交易安全。2026-08-09 曾因測試用的假資料節點直接寫入正式 key，覆蓋掉 `v2_daily_history` 裡 2026-08-02～08-08 共 7 天的真實資料，且找不到任何備份／原始紀錄可以復原（`noda_data.csv` 剛好在同一段期間有 3 週的記錄空窗）。這是本文件把 `v2_daily_history` 列為優先遷移目標的直接原因。

**為什麼這個檔案叫 `global.json`、路徑是這裡**：`C:\Users\homec\.node-red\settings.js` 第 357~364 行的 `contextStorage` 設定：

```js
contextStorage: {
    default: { module: "memory" },
    file: { module: "localfilesystem" }
}
```

`default` 用 `memory`（純記憶體，不落地），`file` 用 Node-RED 內建的 `localfilesystem` 模組（真正寫到磁碟）——這正是為什麼所有 `global.get/set(key, value, 'file')` 呼叫都一定要帶那個 `'file'` 參數，漏了就會落到 `default`（memory），讀寫變成兩個互不相干的儲存空間（`python_ip`、`v2_today` 曾經因此各自出過一次 bug，已修復）。`global.json` 這個檔名跟 `context/global/` 這個路徑結構，是 `localfilesystem` 模組對每個 context scope 的內建命名慣例，不是專案裡任何設定指定的，模組本身也沒有提供自訂檔名的選項——只能透過 `contextStorage.file.config.dir` 改資料夾位置，檔名仍會是 `global.json`。

## 五、若要「統一由 Python 端管理」——三層各自的評估

- **資料層**：投資報酬率最高、風險最低。今日即時資料已經是 Python 在算，缺的只是把「多天歷史滾動」也搬進 Python（自己的持久化檔案，例如 SQLite 或結構化 CSV，取代 Node-RED 的 `v2_daily_history`），順便解決共用 context 檔案的資料安全問題。
- **分析層**：`analytics/` 套件已經是現成的分析層，缺的是（1）正式讓 `cat_health_v3_flow.json` 呼叫 `/api/deviation` 取代自己的 JS 計算（ADR 0001 §2 排定但尚未執行），（2）把 Class C（節律／轉移分析）也搬進 Python——目前這塊仍留在 Node-RED，是 `analytics/README.md`「還沒做的事」列出的項目。
- **監測層**：投資最大的一塊。現在的「個體基線面板」是 Node-RED Dashboard 的 AngularJS 樣板（`ui_template` 節點），連按鈕動作（排除此天、刪除紀錄、存設定）都是靠 `scope.send()` 送回 Node-RED flow 處理，並透過 Node-RED Dashboard 的 websocket 機制即時推送更新（見「排除此天即時更新」的追蹤結果，2026-08-09 討論）。要換成 Python 端管理，等於要重寫一個網頁前端並重做即時推送機制，不是把邏輯搬過去而已。

**初步建議（未定案）**：資料層＋分析層值得做，監測層先不要動——讓 Node-RED Dashboard 降級成「純顯示層」，定期打 Python API 拿資料顯示，不自己算東西。這樣可以拿到「單一事實來源」的好處，又不用花大把時間重造一個網頁前端。

## 八、2026-08-10 執行：搬遷至 `C:\a\global.json`（全部改用 `fs` 手動讀寫）

**做法**：不是只改 `contextStorage.file.config.dir`（那樣路徑會變成 `C:\a\global\global.json`，多一層 `global` 子資料夾），而是依第七節原本評估的「完整方案」——放棄 Node-RED 內建 `localfilesystem` 模組，改用 `fs` 手動讀寫，取得精確路徑 `C:\a\global.json`。

- `settings.js` 的 `functionGlobalContext` 新增 `gfile` 物件（`get(key)`/`set(key,value)`，內部讀寫 `C:\a\global.json`）。
- `貓咪主控.json`、`cat_health_v3_flow.json`（以及正在跑的 `C:\Users\homec\.node-red\flows.json`）裡所有 `global.get(key, 'file')` / `global.set(key, value, 'file')` 呼叫，機械式改成 `global.get("gfile").get(key)` / `global.get("gfile").set(key, value)`。三個檔案全部呼叫點都已確認清空（用「解析 JSON 後在還原出的完整 JS 原始碼上比對」重新掃過一輪，取代掉最初只在單行文字上比對、會漏掉跨行寫法的版本——見下方「事後發現的漏網之魚」）。
- 只動 `global.*(..., 'file')`；`context.get/set(..., 'file')`（例如按鈕統計 `button_stats`／`op_log`）是 node-scoped file context，寫到完全不同的檔案，未受影響、未修改。
- 資料遷移：把當時 `C:\Users\homec\.node-red\context\global\global.json` 的完整內容複製一份到 `C:\a\global.json`，作為新檔案的起始內容，避免搬遷當下遺失既有基線歷史。
- `paper/config.py` 的 `NodeRedConfig.GLOBAL_CONTEXT_PATH` 預設值同步改成 `C:\a\global.json`；`paper/_tools/1_read_context.py`、`paper/node_red_tests/fetch_real_history.py` 兩支唯讀工具也同步改路徑。

**事後發現的漏網之魚（code review 抓到，2026-08-10 同日修正）**：最初用「同一行文字裡同時出現 `global.` 跟 `'file'`」這種單行比對法找呼叫點，漏掉了跨行排版的呼叫（例如「組成 Discord Webhook 格式」節點裡 `global.set(\n "python_ip",\n ip,\n "file"\n)` 這種每個參數各自一行的寫法），導致 `python_ip` 有一條寫入路徑仍停留在舊的 Node-RED file-scope store，跟其他已切到 `gfile` 的讀取路徑對不上。已改用「先把 JSON 解析還原成真正的多行 JS 原始碼、在還原後的文字上比對」的方法重新掃描並修正，且已確認整個 `貓咪主控.json`／`cat_health_v3_flow.json`／`flows.json` 三個檔案裡 `global.*(..., 'file')` 呼叫歸零。

**已知取捨與後續加固**：
- 每次 `set()` 都會觸發 flush（不像原本 localfilesystem 模組每 30 秒才寫一次），對第四節提到的資料遺失事故是更保守的選擇；但最初版本用 `writeFileSync` 直接覆寫正式檔，同一份 code review 指出這在寫入中途當機/斷電時是非原子操作，可能留下半截壞掉的 JSON，而且 `load()` 遇到解析失敗會靜默把 cache 當成 `{}`，下一次 `set()` 就會把這個空物件覆寫回磁碟、等於一次清空所有基線資料——比原本要解決的資料遺失問題更嚴重。已修正：改成非同步 `fs.writeFile` 寫暫存檔＋成功後才 `rename` 覆蓋正式檔（同磁碟區 rename 是原子操作），且解析失敗時不再吞掉例外、直接讓錯誤往上炸給呼叫的 function node（在編輯器顯示紅色錯誤狀態），只有「檔案真的還不存在」這個第一次啟動的情境才視為 `{}`。
- 同一份 review 也指出原本的 `writeFileSync` 是同步阻塞呼叫，在高頻節點（例如「行為統計累積器」約每幾秒觸發一次）上會卡住 Node-RED 單執行緒 event loop；改用非同步 `fs.writeFile` 後不再阻塞，且用一個 `writing`/`pending` flag 讓短時間內多次 `set()` 自然合併成一次落地寫入，不需要額外的 debounce 延遲。

**第二輪 code review（2026-08-10，針對 `貓咪主控.json`／`cat_health_v3_flow.json` 兩個檔案）**：機械式轉換本身確認乾淨（逐一比對轉換前後的 key 名稱，沒有漏改、沒有誤改 `context.*()`）。額外指出 3 點，已處理如下：

1. **try/catch 覆蓋不一致（已修正）**：`偏差分析引擎`、`行為偏差融合引擎`、`個體化基線計算器` 這三個節點裡跟 `v2_baseline` 有關的呼叫，沿用了轉換前就存在的 try/catch 容錯寫法（失敗時退回不落地的 memory scope），但同一支 function 裡其他 key（`v2_daily_history`／`v2_today`／`v2_user_settings` 等）完全沒有包 try/catch。轉換前這個不一致無傷大雅；但 `gfile.load()` 加固後（解析失敗會直接拋例外，見上方「已知取捨」），沒包 try/catch 的呼叫會讓整個 function node 失敗並在編輯器顯示紅色錯誤（明確可見），包了 try/catch 的則會靜默退化成 memory-only、不落地也不報錯——兩種行為並存，且後者恰好違背這次加固「寧可明顯失敗、不要靜默資料異常」的原則。已移除這 3 處 try/catch，改成跟其他呼叫一致的直接呼叫，讓 `C:\a\global.json` 讀寫失敗時全部節點行為一致（明確拋錯，不會有任何一條路徑靜默假裝成功）。
2. **`gfile` 的記憶體 cache 不會被外部寫入自動失效（設計已知限制，暫不處理）**：`cache` 只在 Node-RED process 自己第一次讀取時載入，之後只被自己的 `set()` 更新，不會偵測 `C:\a\global.json` 被其他 process（例如未來 Python 端）修改。目前 Python 端完全不寫這個檔案（只有唯讀工具），所以這個風險目前是休眠的；但如果第六節「資料層」待辦（Python 端寫回歷史資料）真的實作，需要先處理這個 cache 失效問題（例如加 `fs.watch` 或每次讀寫前重新比對檔案 mtime），不是現在就要做。
3. **`gfile` 是自己刻的一套，而不是走 Node-RED 官方的 `contextStorage` 外掛介面（設計取捨，維持現狀）**：review 建議改成正式的 context storage 模組會更乾淨、呼叫點不用全部從 `global.get(key,'file')` 改成 `global.get("gfile").get(key)`。這個方案在第七節評估時就考慮過，但正式模組的非同步/callback 介面規格如果沒對齊會直接讓 Node-RED context 系統整個掛掉（影響範圍不只健康監測，`file` scope 還被其他跟貓咪監測無關的 flow 共用），風險遠高於目前這種「呼叫點都已驗證過、行為可預期」的手動 fs 方案，故維持現狀。

## 九、2026-08-10 執行：Python 端獨立多天歷史（`analytics/daily_store.py`）

**背景**：第六節資料層待辦第一項「設計 Python 端的多天歷史持久化方案」。動機不只是少維護一份重複邏輯——現況下 Python `analytics/` 套件透過 `/api/deviation` 做的「新舊引擎比對」，用的輸入其實是 `analytics_deviation_bridge.json` 把 Node-RED 的 `v2_daily_history` 現撈出來 forward 過去（見 `組成 /api/deviation 請求` 節點），兩邊算的東西**同源**：`v2_daily_history` 一旦被寫壞（第四節那次真實事故），Node-RED 舊引擎跟 Python 比對結果會一起壞掉、比對不出任何異狀。這次要解決的正是這個「同源」問題。

**做法**：讓 Python 端有一份完全獨立收集、獨立持久化的多天歷史，不讀、不寫 Node-RED 的 `global.json` 或任何 Node-RED context，Node-RED 那份 `v2_daily_history`／`daily_history.csv` 完全不動（監測層 Dashboard 依賴的顯示不受影響）。

- 新增 `cat_monitoring_system/analytics/daily_store.py`：SQLite 持久化（`sqlite3` stdlib），`save_day(record)` upsert、`load_history()` 讀取，回傳 `DailyRecord` 列表可直接餵給既有的 `baseline.compute_baseline`。用 SQLite 而非 CSV，是因為 `behavior_segments_log.csv` 已經因為 ISO/本地日期格式混用炸過一次，不想重蹈覆轍；也不需要像 Node-RED 的 `gfile`（第八節）那樣自己刻 atomic write，SQLite 的 transaction 已經夠用。
- 新增 `config.py` 的 `LoggingConfig.DAILY_HISTORY_DB_PATH`（預設 `C:\a\daily_history.db`，可用環境變數 `CAT_MONITORING_DAILY_HISTORY_DB_PATH` 覆寫），刻意跟 `NodeRedConfig.GLOBAL_CONTEXT_PATH`（`C:\a\global.json`）分開存放。
- `trackers/behavior_tracker.py` 的 `check_daily_reset()` 掛上持久化 hook（新增 `_persist_daily_record()`）：跨日重置前，先把「歸零前」的當日累積統計包成一筆 `DailyRecord` 寫進 `daily_store`。這是資料來源的關鍵——Python 端本來跨日時就是直接丟棄前一天資料（沒有彙整成一天的邏輯），這次補上的正是這一段，等同 Node-RED「每日統計彙整」JS function 在 Python 端的對應物，但完全獨立運作。持久化失敗只記警告、不中斷歸零流程（跟 `save_state()` 的容錯原則一致）。
- `server/routes.py` 的 `POST /api/deviation`：`daily_history`／`today` 兩個欄位改成可省略。省略時預設分別讀 `daily_store.load_history()` 與 `frame_processor.tracker.get_today_stats()`（即時資料，扁平化成 `compute_deviation` 要的欄位形狀）；仍接受顯式帶入這兩個欄位當一次性覆寫（測試、手動比對用）。攝影機管線未啟動且沒帶 `today` 時明確回 400，不會靜默當成全 0。
- `analytics_deviation_bridge.json` 的「組成 /api/deviation 請求」節點同步簡化：移除讀取 `v2_daily_history`／`v2_today` 與 ISO 日期正規化的邏輯（那是專屬於 Node-RED 那份歷史格式混用的 workaround，Python 自己收集的歷史從一開始就是 ISO 格式），只保留送 Node-RED 自己管的設定值（`v2_excluded_dates`、`v2_user_settings.baseline_days`、`v2_class_c_score`）。JSON 已驗證語法正確，diff 只動這一個節點的 `func` 欄位。
- 測試：`trackers/tests/test_behavior_tracker_regression.py` 新增兩則（跨日確實持久化到獨立 store／持久化失敗不影響歸零流程）；`server/tests/test_routes_api_regression.py` 的 `TestDeviationRoute` 改寫「缺欄位」相關測試（省略欄位現在是走預設值，不是 400；改用 `FakeTracker` 模擬即時資料來源）。跑過 `pytest`（`cat_monitoring_system/` 下含 GPU 相依模組，需用裝了 `cv2`/`torch` 的環境，例如 `anaconda3/envs/yolo_new`）：337 passed（1 個跟本次變更無關的既有 ST-GCN 模型特徵化測試浮點誤差 flaky 失敗，`processors/tests/test_frame_processor_characterization.py`）。

**效果**：兩份多天歷史各自獨立累積，任一邊被寫壞都不會波及另一邊——例如若 Node-RED 的 `v2_daily_history` 又被誤寫（第四節那種假資料測試節點誤觸生產 key 的情境），Python 這份不受影響，`/api/deviation` 的比對結果會出現真實分歧，等於多一層資料完整性的照妖鏡，而不是像現在這樣「同源，一起壞掉、比對不出異狀」。

**已知取捨**：兩邊各自收集，跨日觸發時機不完全相同（Node-RED 靠 inject 準時 00:00 觸發、若當下沒在跑會整天漏記；Python 是下一次有 frame 進來時 `check_daily_reset()` 才觸發，不受 Node-RED 停機影響但時間點可能差幾分鐘），比對邏輯目前沒有針對這種良性分歧設容許誤差，日後若真的拿新舊比對結果做告警（而不只是人工查看 debug 面板），需要先補這塊，否則會誤報。

**尚未做的事**：`v2_daily_history` 本身仍是第六節待辦——排除日期／刪除紀錄／事件標記這些資料管理動作目前仍只存在 Node-RED context，Python 端的 `daily_store` 目前只有「累積」沒有對應的管理介面；ADR 0001 §2（`cat_health_v3_flow.json` 正式改呼叫 `/api/deviation` 取代自己算 JS）也還沒執行，這次只是讓「比對」用的資料源獨立，不是把新引擎正式扶正。

## 十、2026-08-10 執行：`/dashboard/baseline` 觸發權也收回 Python 端（`dashboard/refresher.py`）

**背景**：第九節只解決了「新引擎算的時候吃誰的資料」，沒解決「誰來觸發算」。實測發現 `/dashboard/baseline`（Python 分析引擎的唯讀展示頁）資料一直不更新——查證後確認 `dashboard/cache.py` 的 `set_latest()` 全專案只有一個呼叫點：`server/routes.py` 的 `POST /api/deviation` handler。而這個端點目前唯一的呼叫來源是 Node-RED 的 `analytics_deviation_bridge.json`（給新舊引擎比對用）。也就是說：即使第九節已經讓資料源獨立，只要 Node-RED 沒開、那個 bridge flow 沒觸發，這個頁面就永遠停在「尚未取得資料」——資料源獨立了，觸發權還在 Node-RED 手上，不算真正「毫無相干」。

**做法**：新增 `cat_monitoring_system/dashboard/refresher.py`：
- `compute_and_cache_once()`：同一個 process 內直接呼叫 `analytics/` 的 `compute_baseline`/`compute_deviation`/`compute_fusion`（不繞 HTTP，不自己打自己的 `/api/deviation`），資料源沿用第九節的 `daily_store.load_history()` + `server/routes.py` 的 `_today_from_live_tracker()`，算完寫進 `dashboard/cache.py`。`class_c_score` 固定用 0（`compute_fusion` 預設值）——Class C 分析還沒搬進 Python，這裡刻意不去讀 Node-RED 的 `global.v2_class_c_score` 來補這個值，否則又會製造一條隱性的 Node-RED 依賴。
- `start_background_refresh()`：啟動一個 daemon thread，每隔 `BaselineDashboardConfig.RECOMPUTE_INTERVAL_SEC` 呼叫一次 `compute_and_cache_once()`。**預設值跟隨 `NodeRedConfig.PUSH_INTERVAL`**（讀同一個環境變數 `CAT_MONITORING_NODERED_PUSH_INTERVAL` 當 fallback 預設，預設 2 秒），感覺跟 Node-RED 面板一樣即時；想獨立於推論推送節奏之外，設專屬的 `CAT_MONITORING_BASELINE_DASHBOARD_RECOMPUTE_INTERVAL` 即可覆寫。`compute_baseline`/`compute_deviation`/`compute_fusion` 都是純 Python 統計運算，配合 `daily_store` 一次輕量 SQLite 讀取，2 秒一次的 CPU 成本可忽略。
- **刻意放在 `main.py` 的 `run_server_mode()` 呼叫，不是 `server/flask_app.py` 的 `create_app()`**：`create_app()` 在測試裡會被重複呼叫驗證旗標開關行為（`dashboard/tests/test_flag_integration.py`），如果背景執行緒的啟動也綁在那裡，每次測試呼叫都會多開一個 daemon thread、且會用預設（正式環境）SQLite 路徑，造成測試互相汙染。這跟 `main.py` 既有的 `_scheduler_loop` 是同一層級的「真正啟動伺服器才會發生」的副作用，維持 `create_app()` 本身純粹、可重複呼叫。
- `main.py` 啟動時印出的網址那段（見前一輪對話）順便補上背景排程啟動的呼叫，都掛在同一個 `if BaselineDashboardConfig.ENABLED:` 底下。
- 測試：新增 `dashboard/tests/test_refresher.py`（4 則：沒有 frame_processor／歷史不足／成功寫入完整 schema／確認不依賴任何 Node-RED 狀態）。跑過 `pytest .`：422 passed（同第九節那個跟本次變更無關的既有 flaky 失敗）。

**效果**：`/dashboard/baseline` 現在資料源（`daily_store` + 即時 tracker）跟觸發（背景執行緒，預設 2 秒一次）都在 Python process 內部完成，Node-RED 開不開、`analytics_deviation_bridge.json` 有沒有部署，完全不影響這個頁面能不能看到最新資料。`POST /api/deviation` 保留原本用途（給 Node-RED 新舊引擎比對用），呼叫時仍會順便更新同一份快取，兩條觸發路徑並存、互不依賴。

**部署當下實測發現的冷啟動問題（已一次性解決）**：`daily_store` 是全新的儲存，一開始是空的——`_persist_daily_record()` 只在真的跨過一次日期邊界時才會寫入一筆，代表要等 7 個真實日曆天過去才會有足夠天數算出基線，在那之前 `/dashboard/baseline` 會一直顯示 `insufficient_data`（畫面上看起來像「數據是空的」）。這不是觸發機制的 bug——背景執行緒確實每 2 秒都有在算，只是算出來的合法結果就是「歷史不足」。解法：新增 `paper/_tools/2_backfill_daily_store.py`，一次性讀取 `NodeRedConfig.GLOBAL_CONTEXT_PATH`（`C:\a\global.json`）的 `v2_daily_history`（Node-RED 已經累積的既有歷史），轉成 `DailyRecord` 灌進 `daily_store`——這正是第七節當初預告「之後要做的話，需要一個轉接層把 `v2_daily_history` 的欄位轉成 `analytics.baseline.DailyRecord`」那件事，現在因為 `/dashboard/baseline` 的冷啟動需求而提前做了。**只搬遷一次，之後兩邊繼續各自獨立累積**，不是讓 `daily_store` 持續讀 `global.json`（那樣又會變回互相依賴）。已在這台機器上執行過一次：`v2_daily_history` 15 筆全數寫入，`compute_baseline` 驗證可正常算出結果（confidence=Medium）。日後若要在其他機器/重新部署時做同樣的事，重跑這支工具即可，冪等（`daily_store.save_day()` 是 upsert）。

## 十一、2026-08-10 執行：兩個影像 plugin 的 Node-RED 端點集中化（config.py 全域參數盤點的產物）

## 十二、2026-08-10 執行：`analytics/` 新增內部 `config.py`，集中管理統計參數並標註文獻依據

**背景**：延續第十一節的全域參數盤點，`analytics/baseline.py`／`deviation.py` 裡有一批模組層級常數（`EWMA_ALPHA`、`MIN_BASELINE_DAYS_DEFAULT`、`MAX_BASELINE_DAYS_DEFAULT`、`MAD_SCALE`、`COUNT_OVERDISPERSION_RATIO` 等）散落在兩個檔案裡，沒有 env 覆寫、也沒有集中的地方一次看完「這些數字為什麼是這樣」。跟 plugin 那批（純操作性設定）不同，這批是統計方法論參數，每個背後的依據強度差很多——直接搬進主 `config.py` 會把數值跟文獻依據拆開；不搬又持續散落。

**做法**：新增 `cat_monitoring_system/analytics/config.py`，比照 `plugins/lick_stage/config.py` 的模式——獨立於主 `config.py`，只在同一個套件內部集中管理，`BaselineConfig`／`DeviationConfig` 兩個 class，每個常數都用四種標籤之一誠實標註依據強度（詳細文字見該檔案開頭 docstring，摘要如下，完整文獻見 `paper/docs/個體化基線與異常偵測文獻來源.md`）：

| 標籤 | 意思 | 例子 |
|---|---|---|
| 【文獻支持】 | 有文獻直接支持這個數值本身 | `MAD_SCALE=1.4826`（Iglewicz & Hoaglin, 1993）；Sanity Check 群體參考值（Eckstein & Hart, 2000） |
| 【與 Node-RED 原版數值一致】 | 移植時對齊舊版 JS 既有值，非獨立校準 | `EWMA_ALPHA=0.15`、`MIN_BASELINE_DAYS_DEFAULT=7` |
| 【工程慣例／專家設定，無直接文獻依據】 | 合理但無文獻校準這個具體數字 | `MAX_BASELINE_DAYS_DEFAULT=30`、`min_daily_monitoring_sec=3600`、`COUNT_OVERDISPERSION_RATIO=1.5`（方向上有 Lindén & Mäntyniemi 2011 支持 NB 優於 Poisson，但 1.5 這個切點本身無校準） |
| 【數值穩定用途，非統計方法論參數】 | 純數值計算安全邊界，不代表統計假設 | `MIN_VARIABILITY_MAD`、`RATE_SMOOTHING_PRIOR`、`MIN_TAIL_P` |

## 十三、2026-08-10 執行：`daily_store` 排除清單 + GUI 歷史資料管理工具

**背景**：Node-RED 的 `v2_excluded_dates` 讓使用者能手動排除某天資料不納入基線計算，但 Python 端獨立的 `daily_store`（第九節）完全沒有對應機制——`dashboard/refresher.py`、`/api/deviation` 在省略 `excluded_dates` 時都是直接當成空清單，沒有任何持久化、可編輯的排除狀態。

**做法**：
- `analytics/daily_store.py` 新增一張獨立小表 `excluded_dates`（只存 `day`，不是在 `daily_history` 上加欄位）——排除是對既有天數的編輯決策，跟原始統計數字是兩件事，分開存也方便日後單獨清空排除清單而不動到任何統計資料。新增 `set_excluded(day, excluded, db_path=None)`（upsert/delete）與 `load_excluded_dates(db_path=None)`（回傳 ISO 字串列表，可直接餵給 `compute_baseline(..., excluded_dates=...)`）。語意對齊 Node-RED 的 `v2_excluded_dates`：排除，不是刪除，資料還在。
- `dashboard/refresher.py` 的 `compute_and_cache_once()` 改成 `compute_baseline(daily_records, excluded_dates=daily_store.load_excluded_dates())`。
- `server/routes.py` 的 `POST /api/deviation`：`excluded_dates` 比照 `daily_history`/`today` 的既有邏輯——省略時預設讀 `daily_store.load_excluded_dates()`；呼叫端（Node-RED）明確帶了（即使空陣列）就以請求內容為準。
- 新增 `cat_monitoring_system/analytics/manage_baseline_history.py`（跟 `baseline.py`/`daily_store.py`/`config.py` 同目錄，2026-08-10 稍晚從原本的 `tools/` 移過來——這支工具本質上就是這幾個模組的操作介面，放在同目錄比放在通用診斷腳本的 `tools/` 更符合「每個子系統自成一體」的擺放慣例）：tkinter 獨立視窗（不需要 Flask/攝影機/Node-RED 任何一個在跑，純讀寫 SQLite），列出 `daily_store` 全部歷史（日期、監測時數、各行為統計、監測時數是否低於 `BaselineConfig.MIN_DAILY_MONITORING_SEC_DEFAULT` 的警示），逐筆勾選「採用」/「排除」，按下「套用變更並重新計算基線」後：(1) 把變更寫進 `excluded_dates` 表，(2) **立即用新清單重新呼叫一次 `compute_baseline` 並顯示結果**（採用天數、信心等級、sanity warning）——這一步是直接證明排除設定真的生效，不是「存了但不知道有沒有用」。
- 測試：`analytics/tests/test_daily_store.py`（新檔案，13 則，補齊 `daily_store.py` 原本就沒有的專屬單元測試，含 upsert/排序/limit_days，以及這次新增的排除功能，含一則端到端驗證「排除一天後 `compute_baseline` 的 `days_count` 真的少 1」）；`dashboard/tests/test_refresher.py`、`server/tests/test_routes_api_regression.py` 各補一則驗證背景排程／`/api/deviation` 兩條路徑都會讀到 `daily_store` 的排除清單。GUI 工具本身用 monkeypatch 掉 `messagebox` 的方式手動驗證過完整流程（載入 15 筆真實資料 → 排除一天 → 套用 → 重新計算顯示「採用 14 天」→ 還原）。跑過 `pytest .`：371 passed（同前幾節那個跟這次變更無關的既有 ST-GCN 特徵化測試 flaky 失敗）。

**已知限制**：GUI 工具跟 `dashboard/refresher.py` 的背景排程是各自獨立觸發（工具本身不會主動去 ping 正在跑的背景執行緒立即重算）——套用變更後，工具自己會立即重算一次證明生效，但 `/dashboard/baseline` 頁面要等背景排程下一個週期（預設 2 秒，見第十節）才會用新清單刷新，通常感覺不出差異；`POST /api/deviation`（Node-RED 呼叫）則是下一次呼叫就會生效。
