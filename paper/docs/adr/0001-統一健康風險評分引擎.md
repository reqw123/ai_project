# 統一健康風險評分引擎，停用貓咪主控.json 的舊版健康引擎與重複 Discord 警示

**狀態**：accepted（2026-08-08）→ 部分撤銷（2026-08-09 續2）→ **重新確認並定案（2026-08-09 續3）**，見文末「分工明確定案」一節；**現況核對（2026-09-04）：Python 端 `analytics/` 已將 `cat_health_v3_flow.json` 的 Class A/B/C 引擎完整移植，數值與本 ADR 決定一致，見文末「現況核對」一節

## 背景

Python 端同時 POST 到 `/yolo_result`（v1，`貓咪主控.json` 接收）與 `/yolo_result_v2`（v2，`cat_health_v3_flow.json` 接收），導致兩個 Node-RED flow **各自獨立**跑一整套健康風險評分：`貓咪主控.json` 用舊版 dScore/fScore/rScore/tScore（30/35/20/15%），`cat_health_v3_flow.json` 用 Class A/B/C 證據融合（45/25/30%，見 `analytics/fusion.py`）。兩者對同一天資料可能算出不同風險等級，且**兩邊 Discord webhook 指向同一頻道**，使用者實際收過對同一狀況判斷不一致的重複通知（2026-08-08 確認）。

## 決定

以 `cat_health_v3_flow.json`（Class A/B/C 融合引擎）作為唯一權威的健康風險評分來源。停用 `貓咪主控.json` 內的「健康引擎分析」「發送提醒→送到 Discord」節點，以及與 `cat_health_v3_flow.json` P1/P2/P5 重複的舊版面板（即時狀態卡片、詳細統計、健康警示、活動力儀表）。

**保留** `貓咪主控.json` 的「儲存CSV」（寫入 `C:\a\noda_data.csv`，`GPT 健康報告.json` 的 GPT 健康報告功能直接依賴此檔案，`cat_health_v3_flow.json` 沒有寫這個檔案）與「影像串流」即時攝影機面板（`cat_health_v3_flow.json` 沒有等效功能）。

## 後果

- 若未來要完全汰除 `貓咪主控.json`，需先把 `noda_data.csv` 輸出與即時影像串流遷移到 `cat_health_v3_flow.json` 或獨立 flow。

## 分工明確定案（2026-08-09 續3）

在「決定撤銷（續2）」之後，2026-08-09 稍晚做了一次針對 `貓咪主控.json`／`cat_health_v3_flow.json` 共用 global context 的 bug 排查（見對話紀錄），發現「兩邊都寫同一個 key」不是理論風險，是實際發生、持續在踩的問題：

- **`v2_today`**：`cat_health_v3_flow.json`「行為統計累積器」寫的版本有完整的 Eckstein & Hart (2000) 百分比欄位（`lick_pct_of_day` 等），`貓咪主控.json`「健康引擎分析」寫的版本沒有這些欄位。兩邊都用 `global.set('v2_today', ..., 'file')` 寫同一個 key，「每日統計彙整」／「跨日資料清除」在午夜或系統啟動時讀到哪一版是非決定性的，會讓當天的 `v2_daily_history` 紀錄悄悄缺欄位。
- **`v2_risk`**：`貓咪主控.json` 寫 dScore/fScore/rScore/tScore 版本，`cat_health_v3_flow.json` 寫 Class A/B/C 版本，兩邊都寫同一個 `v2_risk`，Python 每 ~2 秒推一次資料、兩邊各自算完就覆蓋，**任何時刻讀到的是哪一種評分邏輯是五五波**。更直接的後果：`analytics_deviation_bridge.json`「比對新舊引擎結果」節點讀 `global.get('v2_risk')` 當作「cat_health_v3 舊引擎」的比對基準，但實際上這個 key 有機率被貓咪主控的 dScore 結果污染，代表先前蒐集的「新舊引擎比對」數字可信度有疑慮。

**決定**：徹底終結「兩邊都寫」這個問題根源，而不是幫其中一邊的 key 改名共存。重新確立分工——**`貓咪主控.json` 只負責監控（影像串流、CSV 記錄、行為時間軸），不做任何健康分析／風險評分；`cat_health_v3_flow.json` 是唯一的分析與評分來源**。這次不是暫時性的比對期安排，是定案。

**執行**：
- `貓咪主控.json`「數據分發器」（id `524a127640fe5d6c`）第 5 個輸出（原接「健康引擎分析」）改回空陣列，其餘 6 個輸出（即時狀態卡片、行為時間紀錄、詳細統計、活動力儀表、建立CSV、事件時間軸引擎）不受影響。
- 「健康引擎分析」（連帶下游「健康警示」「發送提醒」「送到 Discord」）節點本體保留在檔案中未刪除，只是失去上游輸入——此節點是 `v2_today`／`v2_hourly`／`v2_transition_matrix`／`v2_risk` 四個 key 的唯一寫入來源，切斷輸入後 4 個 `global.set()` 都不會再執行，Bug 1、Bug 2 從根源解決，不需要另外改 key 名稱。
- **已知副作用**：`貓咪主控.json` 自己儀表板上的「健康警示」卡片會停止更新（因為餵它資料的節點失去輸入）。這是「分工明確」下的必然結果——健康分析結果本來就不該出現在監控用的儀表板上，要看風險評分請看 `cat_health_v3_flow.json` 的 Dashboard（P1～P4）。
- 尚未執行：需使用者在 Node-RED 編輯器匯入更新後的 `貓咪主控.json`（Replace existing flow）→ Deploy。

## 現況核對（2026-09-04，依 `cat_monitoring_system/analytics/{fusion,baseline,deviation,config}.py` 程式碼核對）

> [!NOTE]
> 本節只**核對本 ADR 的決定是否仍與現況相符並補充現況資訊**，不更動、不刪除上面的決定與執行紀錄。

**✅ 決定本身依然成立，且已被進一步落實到 Python 端**：本 ADR 決定「以 `cat_health_v3_flow.json` 的 Class A/B/C 融合引擎為唯一權威健康風險評分來源」。目前 `cat_monitoring_system/analytics/fusion.py` 是這套引擎的 **Python 移植版**（模組 docstring 明載「port of 行為偏差融合引擎...from `cat_health_v3_flow.json`」），且權重／門檻與 Node-RED 原版**數值上完全一致**，直接核對如下：

| 項目 | ADR 描述 | `analytics/fusion.py` 實際值 | 是否一致 |
|---|---|---|---|
| Class A/B/C 融合權重 | 45/25/30% | `FUSION_WEIGHTS = {"class_a": 0.45, "class_b": 0.25, "class_c": 0.30}` | ✅ 一致 |
| Class A 內部特徵權重 | 未在 ADR 中列出細節 | `lick_time=0.30, lick_count=0.15, scratch_time=0.30, scratch_count=0.10`（合計 0.85） | — |
| Class A override 門檻（sigma） | 未在 ADR 中列出細節 | `CLASS_A_THRESHOLDS = {"mild": 2.5, "moderate": 3.0, "severe": 4.0}` | — |
| 風險等級分數門檻 | 未在 ADR 中列出細節 | `Normal<20 / Mild<45 / Moderate<70 / Severe≥70` | — |

**這套引擎目前是獨立於攝影機管線、跨天彙整後才計算的「個體化基線分析」層**（見 `ARCHITECTURE.md` §3：`daily_store → baseline → deviation → fusion → /dashboard`），與本 ADR 討論的「即時 Python → Node-RED 兩份 flow 各自算」場景相比，代表 Class A/B/C 引擎的權威地位已經從「Node-RED 端唯一權威」進一步延伸為「Python 端也有一份數值一致的權威實作」，兩者互為比對（`POST /api/deviation` 端點即用於新舊引擎比對，與本 ADR 執行紀錄提到的 `analytics_deviation_bridge.json`「比對新舊引擎結果」節點相呼應）。

**⭐ ADR 未提及、但現況已存在的實質強化**：`fusion.py` 的 sigma 值來源已不是單純 `(x-mean)/std`，而是依指標型態分流：連續指標（如 `lick_time`/`scratch_time`）用穩健 z-score（中位數／MAD），稀疏計數指標（如 `lick_count`/`shake_count`）用 Poisson 或過度離散時退回負二項分布的尾機率模型（見 `analytics/deviation.py`）。這是本 ADR 決定當時（Node-RED JS 版）沒有的統計方法改進，屬於移植後的後續演進，不影響本 ADR「唯一權威來源」這個決定本身。

**⚠ 誠實揭露（`analytics/config.py`、`fusion.py` 原始碼註解本身即如此標註，非本次新增判斷）**：融合權重（45/25/30%）與 sigma 門檻（2.5/3.0/4.0）目前仍是專家經驗值，**沒有資料驅動校準**；`fusion.py` 原始碼註解進一步指出，「Class A > Class C > Class B」這個權重排序背後假設的文獻支持，經 2026-08 的文獻掃描核對後**並不成立**（Lopes et al. 2021 與 Merck Veterinary Manual 均將「自我理毛減少」與「活動力下降」視為同一套 sickness-behavior 症候群裡同樣非特異性的共現表現，而非有主從關係的證據強度層級）。這與本 ADR 的「唯一權威來源」決定是兩個不同層次的問題——**決定「誰是唯一評分來源」依然成立，但那個來源本身的統計假設仍待日後用真實診斷標記資料重新校準**，論文中應誠實列為限制（詳見 `paper/docs/個體化基線與異常偵測文獻來源.md` §3）。

**未能在本次核對範圍內驗證的部分**：ADR 內文多處提到需要「使用者在 Node-RED 編輯器手動匯入／Replace existing flow → Deploy」的步驟（例如「分工明確定案」一節末的部署動作）——這些屬於 Node-RED flow 檔案與部署操作，不在本次可讀取的 Python 原始碼範圍內，因此**無法確認是否已實際部署執行**，仍以 ADR 原文的「尚未執行」為準，這裡不做狀態變更。

**與 SQA（骨架品質評估）的關係**：`processors/skeleton_quality_assessment.py` 的幾何否決機制只作用在 ST-GCN 行為分類的信心門檻（覆蓋為 `LOW_CONF_ID`），並未被 `analytics/fusion.py`／`baseline.py`／`deviation.py` 直接引用——即 SQA 對健康風險評分引擎是**間接**影響（透過上游行為標籤的可信度，間接影響進入 `BehaviorTracker` 的行為時長/次數統計），不是本 ADR 決定範圍內的直接耦合，這裡僅誠實記錄查證結果，不代表需要修改本 ADR 的決定。
