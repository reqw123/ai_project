M5

身體尺寸估算與不確定性

高優先（最快補齊）
送了沒人讀 / 沒有對應卡片

候選命中分數有送但沒讀取；「模稜兩可」統計也有送，但部位時長面板只有五張既有 卡片，沒有幫這個新判定開一張——使用者在儀表板上完全看不到這項新功能算出來的 結果。兩個既有欄位，補一張卡片就能接上，投報率最高。

geometry_score ambiguous_time ambiguous_hits ambiguous_pct
位置
  • Python 端來源：LickResult.to_payload()（models.py）
  • Node-RED：「舔舐部位分析器」function 沒有讀取 geometry_score；「P2 部位時長統計」ui_template 的 ZONE_LIST 陣列只有 BODY/FL/FR/HL/HR 五項，沒有 AMBIGUOUS
M6

事件邊界判定與跨模組驗證

低優先（跟 M2 一起處理）
從未送到 Node-RED

換部位次數、bout 有沒有被切分過，以及這次新做的「兩套判定邏輯互相驗證」結果， 全部是事件層級欄位，跟 M2 同樣的缺口——只進資料庫，沒有推送機制。

zone_switch_count raw_bout ext_zone_mode ext_zone_l1_mode ext_zone_confidence_mean
位置
  • Python 端來源：plugins/lick_stage/bout_aggregator.py::_ActiveBout.to_event()（跟 M2 同一個字典）

建議處理順序

  1. M5：補「模稜兩可」卡片＋顯示 geometry_score
    兩個既有欄位已經在 payload 裡，只差 Node-RED 端補一張卡片跟兩行讀取，工程量最小、使用者感受最直接。
  2. M1：把 frame_state／reason_code 顯示出來
    同樣是欄位已經在 payload 裡，差在 Node-RED 端沒組進輸出；補上之後使用者才看得出「現在貓咪是哪一種狀態」，而不是只有部位統計。
  3. M2 + M6：設計事件層級的推送機制
    工程量最大——需要決定新端點的 schema、推送時機（bout 關閉時 vs. 定期批次）、跟現有逐幀 payload 的關係，建議獨立排一次任務，不要跟前兩項混在一起做。
  4. M4：pose_quality 等 M2/M6 做完後一起帶出去
    這個分數本質上是「事件」層級的統計量（平均值），沒有獨立處理的必要，跟著事件推送機制一起接上即可。
