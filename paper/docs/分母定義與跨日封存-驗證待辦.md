## 一、這次修了什麼（一句話版）

| # | 問題 | 修正 |
|---|---|---|
| 1 | 午夜寫入：程式跑過午夜 → Node-RED 漏記前一天；午夜前關程式 → Python 漏記前一天 | 兩邊都能記到。Node-RED 跨日時先把前一天暫存到 `v2_today_prev`；Python 下次啟動會把舊日期的存檔補寫進 `daily_history.db`；每小時分布另存 `v2_hourly_persist`，關機隔天補封存時段資料仍在 |
| 2 | 分母不一致：`monitoring_seconds` 名稱像運行時間，實際是貓在畫面時間；時段模式的比例又用運行時間當分母；`cat_visible_seconds` 扣兩次 | 三個時間在 tracker 逐幀累加（見下方定義）；全天與時段模式的比例分母都改成「貓在畫面時間」；扣兩次的 bug 已修 |
| 3 | 收錄門檻 | 封存到歷史的條件：**系統有運行過就封存**（2026-09-30 起拿掉原本「運行 ≥ 30 分鐘」的門檻，見 [`封存門檻移除-待辦.md`](封存門檻移除-待辦.md)）；能不能進基線看**貓在畫面**：全天模式 ≥ 1 小時、時段模式 ≥ 30 分鐘 |
| 4 | 每小時資料分不出不在畫面／無法判定；時段資料沒進 Python DB | 每小時多 `visible_sec` / `not_detected_sec` / `low_conf_sec`；`daily_history.db` 新增運行時間、不在畫面、low_conf 三來源與 `periods` |

另外修了一個排程相關的 bug：排程暫停（例如 18–24 以外）隔天恢復時，第一幀會把十幾個小時灌進當下那一小時。現在兩幀間隔超過 `MAX_FRAME_GAP_SECONDS`（預設 5 秒）就視為中斷、不計時。

### 定義（2026-09-29 使用者確認）

```
系統運行時間 run_seconds        ＝ 貓在畫面 ＋ 貓不在畫面（逐幀累加，中斷的空白不算）
貓在畫面時間 monitoring_seconds ＝ 五類行為 ＋ low_conf          ← 比例指標分母、基線收錄門檻
貓不在畫面   not_detected_time  ＝ YOLO 連續超過 5 幀沒偵測到目標貓
low_conf（貓在畫面但行為無法判定）＝ warmup（窗口未滿 16 幀）＋ uncertain（ST-GCN 信心不足）＋ sqa（骨架品質不通過）
```

每小時／每時段：`monitoring_sec` 仍是**系統運行**（判斷時段有沒有被監控），`visible_sec` 才是貓在畫面。
