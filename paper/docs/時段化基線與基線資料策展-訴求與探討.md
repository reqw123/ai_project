## 一、兩項訴求（原話 + 展開）

### 訴求 1（原話）

> 雖然系統分為 4 個時段，但實際上要錄製 24 小時非常困難。實際做論文驗證時我大概只會從 4 個時段挑兩個時段出來做數據分析，而現在系統是整天為單位計算。後續如果做單一時段異常評估，權重也會受影響。

**展開**：

- 系統把一天切成 4 個時段：`00-06` / `06-12` / `12-18` / `18-24`（`每日統計彙整` 節點的 `hourly` → `periods` 對應表）。
- 但目前**只有「涵蓋率統計」用到時段**——基線的均值／標準差／偏差分數／融合風險，全部是**整天彙總值**在算。
- 驗證期若每天只錄 2 個時段、且**哪 2 個時段每天不固定**，整天彙總會被「今天取樣到貓的哪段作息」污染。
- 未來若要做「單一時段的異常評估」（例如只看深夜 `00-06` 是否異常），現行為整天調校的融合權重直接套用會失真。

### 訴求 2（原話）

> 目前健康檢測 v2 雖然可以自選要採用的基線資料有哪幾筆，但具體只知道該筆資料缺少哪個時段，而不知道該筆資料那天貓咪的行為軌跡是怎麼樣的。

**展開**：

- v2 可以逐筆勾選「這天計入／不計入基線」（`v2_excluded_dates` / `daily_store.set_excluded()`）。
- 但選取介面只顯示：日期、監測秒數、`OK`/`SHORT`、`[EXCLUDED]`、時段涵蓋率。
- 使用者要判斷「這天是**真的異常**（→排除）、**錄製瑕疵**（→排除）、還是**正常變異**（→保留）」，手上資訊不足——看不到那天各指標的實際數字、相對基線偏多少、行為在時間軸上怎麼分布。

## 二、訴求 1：整天基線 vs. 只錄部分時段

<a id="sec-2-1"></a>
### 2.1 問題本質：晝夜節律混淆（不只是時數變少）

> 📖 **一句話摘要**：貓的行為率強烈依時段，只錄部分時段等於「取樣到貓的一部分作息」，把不同作息組成的日子放在一起比，基線就被污染了。

貓有明顯的**晝夜節律（circadian rhythm）**，各行為的發生率依時段差異極大：

| 時段 | 典型行為組成 |
|---|---|
| `00-06` | 幾乎在睡：低 walk/lick、高 stop |
| `06-12` | 過渡：晨間活動、進食 |
| `12-18` | 最活躍：高 walk、中等 lick |
| `18-24` | 次活躍：黃昏活動高峰 |

現行每個指標（`lick_time`、`walk_time`、`active_ratio`…）都是**整天彙總**，基線是這些每日彙總值的 `mean`/`std`。

若驗證期每天只錄 2 個時段、而且哪 2 個每天不一樣：

| 指標類型 | 會發生什麼 |
|---|---|
| **絕對值**（`lick_time` 秒） | 只錄早上的那天 `lick` 總量遠低於錄下午+晚上的那天 → 純粹取樣差異，但基線 `std` 被灌大，真正的異常被埋掉 |
| **比例值**（`lick_pct_of_active`、`active_ratio`） | 半修正了「錄幾小時」的問題，但**沒修正組成問題**：偏早上的那天 `active_ratio` 天生偏低（不是貓生病，是你取樣到牠的睡眠時段） |

> [!WARNING]
> **`MIN_DAILY_MONITORING_SEC` = 3600（1 小時）那個門檻擋不了這個問題。**
> 它只過濾「幾乎全空」的天，不管「錄了 5 小時但都是睡覺時段」這種組成偏差。

### 2.2 現況盤點（程式碼層級）

<a id="sec-2-3"></a>
### 2.3 為什麼比例指標只能半修正

Eckstein & Hart (2000) 三層改革引入的比例指標（`lick_pct_of_day`、`lick_pct_of_active`、`active_ratio`、`rest_ratio`）本意是讓「今天監控/在畫面時間比昨天長或短」不影響判斷。它確實解決了**時數**問題，但：

- `active_ratio` 在 `12-18` 可能是 60%，在 `00-06` 可能是 10%。
- 「偏下午的錄製日」whole-day `active_ratio` 天生偏高、「偏早上的錄製日」天生偏低。
- 兩者放進同一條基線 → `std` 膨脹、或系統性偏移。

> 🧠 **原理**：比例指標把分母從「絕對時間」換成「當日總時間/活動時間」，但**分子和分母都還是整天的加總**，加總的內容取決於你取樣到哪些時段。要真正消除節律混淆，分子分母都得限縮在**同一個時段**內比較。

<a id="sec-2-4"></a>
### 2.4 權重問題

Python `fusion.py` 現行權重（為**整天**調校）：

```
CLASS_A_FEATURES = { lick_time:0.30, lick_count:0.15, scratch_time:0.30, scratch_count:0.10, ... }   # 和 = 0.85
CLASS_B_FEATURES = { shake_count:0.40, walk_time:0.30, stop_time:0.30 }
FUSION_WEIGHTS   = { class_a:0.45, class_b:0.25, class_c:0.30 }
```

> [!WARNING]
> 拿整天權重去評**單一時段**會失真：
> - 評 `00-06`（睡眠時段）時，`walk_time` / `scratch` 這些本來就趨近 0 的指標會產生**噪音偏差分**；
> - `stop_time`（靜止）在該時段本來就該主導，卻只拿到整天權重；
> - `head_shake` 這種跟時段幾乎無關的指標，權重不該隨時段變。
>
> → 單時段評估需要**各時段自己的權重輪廓**，或至少「該時段適用哪些指標」的白名單。

<a id="sec-2-5"></a>
### 2.5 文獻定位

> [!IMPORTANT]
> 文獻**已經指向時段粒度**，是實作沒跟上。

- **Silva, Ribeiro & Gama (2025)**（[`個體化基線與異常偵測文獻來源.md`](個體化基線與異常偵測文獻來源.md) 已收錄，標註「建議重點引用」）：10 隻寵物（5 貓 + 5 狗）加速度計連續監測，比較時間聚合窗口 × 3 種非監督演算法，**結論「每日資料再切分時段」聚合效果最佳**——與本專案「個體逐日基準＋按時段切分」設計最直接對應的前例，物種涵蓋貓。
- **Wagner et al. (2021)**：牛的晝夜節律異常對疾病的偵測率達 95%，間接支持 Class C（節律）有實質診斷價值。
- `baseline.py` 模組 docstring 自己就寫：Silva 2025「per-day-then-time-of-day aggregation works best — the same granularity this module's `period_coverage` tracking already uses」。

<a id="sec-2-6"></a>
### 2.6 選項 A / B / C / D

| | 做法 | 優點 | 代價 / 風險 |
|---|---|---|---|
| **A. 時段化基線**（正統） | 記錄單位 `(天, 指標)` → `(天, 時段, 指標)`；每指標算 4 條基線；今天錄到哪些時段就各自比對該時段基線，再只用「有錄到」的時段加權彙總；`MIN_BASELINE_DAYS` 變成 per-period（要 N 天「有 06-12 的資料」才有 06-12 基線） | 統計正確；晝夜混淆消除；直接支援單時段評估；文獻背書（Silva 2025） | 資料需求 ×4（見 [2.7](#sec-2-7)）；`daily_history.db` 加 period 維度（新表 `period_history` 或加欄位）；Node-RED `個體化基線計算器` + Python `baseline.py`/`deviation.py` 都要改；`fusion.py` 權重要加時段層；`manage_baseline_history.py` 策展工具要時段化 |
| **B. 時段正規化的整天指標**（折衷） | 保持整天運算，但用「各時段佔比輪廓」把當天只錄到的時段放大成「全天等效值」 | 不動 schema；引擎改動小 | 需要可靠的時段輪廓（沒錄過完整天 → 雞生蛋）；正規化放大噪音；**仍無單時段異常偵測**（訴求 1 後半段沒解決） |
| **C. 固定時段對 + 當成「單位」** | 論文期間**每天都錄同樣 2 個時段**（建議 `12-18` + `18-24`，活動量最高）。「天」＝那個固定 10 小時窗，構造上就可比 | **零程式改動**；論文最乾淨（受控協定）；寫作一句話交代「觀測窗標準化為 12:00–24:00」 | 不能推論到未觀測時段；之後想做時段拆分要重新蒐集；損失晝夜覆蓋 |
| **D. C ＋ 現在就把時段資料寫進 DB** | 論文走 C，同時把 `每日統計彙整` 已算好的 `periods` 落地到 `daily_history.db`（新表，不影響現有計算） | 成本≈0（資料已存在）；未來要做 A 不用從頭蒐集 | 需要一次 schema migration + `每日統計彙整`/`daily_store` 各補幾行 |

<a id="sec-2-7"></a>
### 2.7 資料需求試算

假設驗證期每天穩定錄 2 個時段：

| 方案 | 每天得到的「基線樣本」 | 要達到 `MIN_BASELINE_DAYS = 7` 需要 |
|---|---|---|
| C（固定時段對） | 1 筆（那個固定 10 小時窗） | **7 個錄製日** |
| A（4 時段各自基線，時段輪流） | 每時段每 2 天 +1 筆 | 每個時段要 7 筆 → **約 14 個錄製日**（且要平均分配 4 個時段）；某時段運氣不好少錄 → 那條基線一直不成立 |
| A（只做 1 個時段） | 那 1 個時段每天 +1（若每天都錄它） | **7 個錄製日**（跟 C 一樣，但只覆蓋 1 個時段） |

> 📌 **本小節結論**：全 4 時段的方案 A 在「錄製本身就是瓶頸」的前提下，資料負擔約為 C 的 2 倍且更脆弱。方案 A 若要做，**縮到 1 個時段**才務實。

<a id="sec-2-8"></a>
### 2.8 對論文的影響

| 論文主張 | 對應方案 | 方法學交代 |
|---|---|---|
| 「個體化**整天**基線異常偵測」 | C（＋D 備料） | 「因連續 24 小時錄製不可行，觀測窗標準化為活動量最高的 12:00–24:00 兩時段，作為個體基線與偏差評估的一致單位。」 |
| 「**時段級**異常偵測」是貢獻之一 | A（scope 到 1 個時段）| 需明說是 proof-of-concept，樣本受限於單一時段；引用 Silva 2025 作為方法學前例 |

> ✅ **Best Practice**：論文需要「乾淨、可辯護的協定」的程度，遠高於「通用系統」。固定時段對是一句話能講清楚的方法學決定；全時段化基線是會拖累資料蒐集、又難在有限樣本下驗證的工程投資。

<a id="sec-2-9"></a>
### 2.9 本節建議與待決策

**建議**：

- **論文時程**：**C + D**。
  - C：驗證期固定錄 `12-18` + `18-24`（或使用者實際能穩定錄的那 2 個時段，但**每天一致**）。
  - D：新增 `daily_history.db` 的 `period_history` 表，`每日統計彙整` / `daily_store` 各補幾行把 `periods` 落地。純備料，不改任何現有計算。
- **除非**論文貢獻就是要展示單時段偵測 → 方案 **A 縮到 1 個時段**，並在 `fusion.py` 為該時段設專屬權重白名單。

**待決策問題**：

1. 論文的**貢獻主張**是「整天個體化基線」還是「時段級偵測」？→ 決定 C vs A。
2. 驗證期能**穩定錄到的固定時段對**是哪 2 個？
3. 要不要現在就做 D（備料）？（建議要，成本低）

<a id="sec-3"></a>
## 三、訴求 2：基線資料策展看不到行為軌跡

<a id="sec-3-1"></a>
### 3.1 訴求展開

挑選基線資料時，使用者要回答的問題是：

> 這天是**離群值**，因為 (a) 貓真的異常 → 排除（否則污染基線）、(b) 錄製瑕疵 → 也排除、還是 (c) 只是正常變異 → 保留？

現行介面（`manage_baseline_history.py` GUI / Node-RED P4 面板）只給：日期、監測秒數、`OK`/`SHORT`、`[EXCLUDED]`、時段涵蓋率。**判斷 (a)/(b)/(c) 的資訊不足。**

<a id="sec-3-2"></a>
### 3.2 判斷「排除 vs 保留」需要的資訊

| # | 需要看到 | 為什麼 |
|---|---|---|
| 1 | 那天**各指標的值 vs 目前基線**（每指標 z-score） | 直接回答「這天是不是在拉基線」。例：「這天 lick 高 3.1σ、walk 0.2σ、stop 低 1.1σ」 |
| 2 | 時段涵蓋率**帶各時段實際值**，不只「缺 00-06」 | 分辨「缺時段」是「沒錄」還是「錄了但那時段貓沒出現」 |
| 3 | 一條 **mini 行為軌跡**（時段/每小時分布 bar） | 看出「14–17 點活躍然後就沒了」vs「整天平穩」——前者可能是錄製中斷，後者是正常 |
| 4 | 那天的**事件標註**（`v2_event_tags`） | 使用者當時記的上下文：「獸醫回診」「訪客」 |

> ⭐ **最有用的單一新增：第 1 項（z-score vs 目前基線）**——它把抽象的「這天奇怪嗎」變成具體數字。

<a id="sec-3-3"></a>
### 3.3 現況盤點：資料在哪

| 資料 | 位置 | 粒度 | 策展工具現在有沒有用 |
|---|---|---|---|
| 每日彙總（walk_time / lick_count / stop_time…） | `daily_history.db` ✅ | 整天 | 只顯示 `monitoring_seconds` |
| 時段細分（`periods` 子物件） | `global.json` 的 `v2_daily_history` | 4 時段 | 只算涵蓋率 `{covered,total}` |
| 每小時分布（`v2_hourly`） | Node-RED，**每天覆蓋、不留歷史** | hour | 無 |
| 事件標註（`v2_event_tags`） | `global.json` | 手動 | 無 |
| 當日 risk 分數 | `v2_daily_history[].risk`（若算過） | 整天 | `_tools/1_read_context.py` 有印，GUI 無 |

> 💡 判斷用的**整天資料已經在 `daily_history.db`**；`compute_baseline()` 很便宜（一次輕量 SQLite 讀 + 統計）。→ 選項 1 和 3 不需要 schema 改動。

<a id="sec-3-4"></a>
### 3.4 選項 1 / 2 / 3

| | 做法 | 需要 | 工作量 |
|---|---|---|---|
| **1. 強化現有清單** | 每筆日期列加：<br>① 各指標 vs 目前基線的 z-score（顏色：綠 <1σ / 黃 1–2σ / 紅 >2σ）<br>② 一行摘要「walk 42min / lick 18min / stop 5.2h / active 31%」<br>③ 點開展開 4 時段表 | 只用 `daily_history.db` 現有資料 + 即算 `compute_baseline()` | 小（~半天～1 天） |
| **2. 單日軌跡視圖** | 點某天 → 每小時堆疊 bar（walk/lick/scratch/stop）＋事件標註＋當日轉移矩陣 | 每日**每小時**資料要持久化（`每日統計彙整` 要 snapshot `hourly` 進每日紀錄；目前被清空）→ schema 改動 | 中（含 Node-RED 改動 + migration） |
| **3. Leave-one-out 影響預覽** | 選/hover 某天時顯示「排除這天 → 基線 mean 位移：lick 62→58min、std 12→9」 | `compute_baseline()` 算有/無兩版取差；`manage_baseline_history.py` 本來就在 toggle 時重算，只是把 delta 顯示出來 | 小 |

<a id="sec-3-5"></a>
### 3.5 本節建議與待決策

**建議**：**選項 1 ＋ 3**，先做在 `manage_baseline_history.py`（Python 工具好迭代，認真的基線策展本來就該在這裡做；Node-RED P4 面板維持簡單）。

- 選項 1：每列加「vs 目前基線 z-score」＋一行指標摘要。
- 選項 3：選取時加「leave-one-out 基線位移預覽」。
- 選項 2（每小時軌跡）**除非論文需要，先不做**——它要動 Node-RED + schema。

**待決策問題**：

1. 平常挑資料是用 Python `manage_baseline_history.py` 還是 Node-RED P4 面板？（決定先做哪邊）
2. 論文有沒有要在文中「展示某幾天為什麼被排除」？→ 若有，選項 2 的每小時軌跡圖有價值。

## 四、兩項訴求的交互關係

```
                    訴求 1 決策
                   /            \
         走 C / B（整天為單位）    走 A（時段化基線）
                |                      |
   訴求 2 = 選項 1+3（整天 z-score）   訴求 2 必須時段化：
   —— 可獨立先做，不等訴求 1          每筆要顯示「各時段 vs 該時段基線」
                                       的 z-score，選項 1 的「一行摘要」
                                       也要拆成 4 時段
```

| 情境 | 訴求 2 的策展工具長怎樣 |
|---|---|
| 訴求 1 走 **C / B** | 選項 1 = 每筆一組整天 z-score；選項 3 = 整天基線位移。**現在就能做。** |
| 訴求 1 走 **A** | 每筆要展開成 4 時段 × 各指標的 z-score（相對該時段基線）；「缺時段」不再是缺陷而是正常（那天就只錄那 2 個時段）；leave-one-out 要 per-period 算 |

> [!IMPORTANT]
> **順序建議**：訴求 2 的選項 1+3 先做（整天版，低成本、立即有用）。訴求 1 若之後決定走 A，再把策展工具升級成時段版——不會白工，整天 z-score 的顯示邏輯可複用。
