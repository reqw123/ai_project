# 測試操作手冊

給第一次接觸這套測試的你看的操作指南。這份文件只講「怎麼用」；設計理念與函式分類請看 [0_測試策略分析.md](0_測試策略分析.md)。

---

## 一、先搞懂幾個名詞

- **單元測試 (Unit Test)**：針對一個函式，給固定輸入，斷言輸出等於「你手算/推導出來」的正確答案。適合邏輯簡單、可以人工驗證的函式（純函式）。斷言的是「這個答案本來就該是這樣」，不是「反正現在輸出這樣」。
- **特徵化測試 / 回歸測試 (Characterization Test / Regression Test)**：適合邏輯太複雜、牽涉真實模型/GPU，沒辦法手算正確答案的情況。做法是：先把「目前系統對某個固定輸入的實際輸出」凍結成一份**快照 (Snapshot)** 檔案，之後每次跑測試，都拿「現在的輸出」跟這份快照比對。
  - 這種測試**不保證輸出是對的**，只保證「沒有在你不知情的狀況下被改變」。
  - 好處：可以幫還沒有測試保護的舊程式碼（例如 `FrameProcessor.process()`）先建立一張安全網，之後才敢放心重構。
- **API Regression Test**：針對 Flask 路由（`server/routes.py`），驗證的是「API 的對外契約」——HTTP 狀態碼、回應 JSON 有哪些欄位（schema/keys）、錯誤處理是否符合預期。**刻意不驗證任何演算法/推論結果的正確性**（那些已經在上面兩種測試涵蓋過），只確保未來重構路由內部實作時，前端/Node-RED 呼叫這些 API 的方式不會被悄悄破壞。
- **快照 (Snapshot)**：一份 JSON 檔案，記錄「基準行為」。只有 Regression/Characterization Test 會用到快照；Unit Test 與 API Regression Test 都是直接斷言明確的期望值/schema，不用快照。測試時只負責「比對」，**不會自動幫你重新產生**——這是刻意設計，避免快照被不小心刪除後，測試自動重建、永遠通過、卻失去了偵測問題的能力。

## 三、環境需求

專案裡有兩個會用到的 Python 環境：

- **base 環境**（你平常開終端機預設的那個）：沒裝 `torch`/`cv2`/`ultralytics`/`flask`。只能跑不需要這些套件的測試（170 個）：`analytics/tests`、`trackers/tests`、`utils/tests`、`paper/tests`（config.py）。
- **`yolo_new` conda 環境**：裝了完整的 GPU/YOLO/ST-GCN/Flask 依賴，**跑全部 428 個測試都要用這個**。

```powershell
conda activate yolo_new
```

不確定現在是哪個環境，看提示字元前面有沒有 `(yolo_new)`。

⚠️ **有些「明明是純函式、不用 GPU」的模組，在 base 環境還是會被整批跳過**（例如 `plugins/lick_stage/` 底下的幾何函式、`server/routes.py` 裡的 `_daily_record_from_dict()`）。這不是測試寫錯，是因為這些檔案的 import chain 會間接拉到 cv2/torch/flask（細節見第六節 6.5）。

## 四、常用指令

**你習慣待在 `C:\ai_project` 開發，以下指令都假設你在那個目錄。**

### 4.1 跑全部測試

```powershell
cd C:\ai_project
conda activate yolo_new
python -m pytest -v
```

裸執行 `pytest`（不給路徑）會自動只掃描 `pytest.ini` 裡登記的測試資料夾，不會誤觸專案裡其他無關的腳本。

### 4.2 只跑不需要 GPU 的測試（隨便什麼環境都行，速度快）

```powershell
python -m pytest paper/cat_monitoring_system/analytics/tests paper/cat_monitoring_system/trackers/tests paper/cat_monitoring_system/utils/tests paper/tests -v
```

### 4.3 只跑某一個模組 / 某一個階段

```powershell
# 只跑 Phase 1（Characterization / Regression Test）
python -m pytest paper/cat_monitoring_system/trackers/tests/test_behavior_tracker_regression.py paper/cat_monitoring_system/processors/tests/test_frame_processor_characterization.py paper/cat_monitoring_system/processors/tests/test_golden_dataset.py -v

# 只跑 Phase 2（Unit Test）某個優先序項目，例如 plugins 幾何函式
python -m pytest paper/cat_monitoring_system/plugins/tests -v

# 只跑 API Regression Test
python -m pytest paper/cat_monitoring_system/server/tests/test_routes_api_regression.py -v
```

### 4.4 只跑名稱包含某個關鍵字的測試

```powershell
python -m pytest -k "scratch" -v          # 只跑名稱或參數含 "scratch" 的測試
python -m pytest -k "alerts" -v           # 只跑警報相關的測試
python -m pytest -k "overlay" -v          # 只跑 /api/overlay 相關的測試
```

### 4.5 其他好用參數

```powershell
python -m pytest -v -s              # -s：顯示 print 輸出（例如模型載入訊息）
python -m pytest --collect-only -q  # 只列出有哪些測試，不執行
python -m pytest -x                 # 遇到第一個失敗就停止，不繼續跑後面的
python -m pytest --tb=short         # 測試失敗時，錯誤訊息只顯示精簡版
```

## 五、快照怎麼用

**只有 Phase 1（Characterization / Regression Test）才有快照**；Unit Test 跟 API Regression Test 都是直接斷言明確答案/schema，沒有快照檔案要管理。

### 5.1 平常跑測試 —— 不用管快照

`python -m pytest ...` 只會**讀取**既有快照做比較，不會自己產生或修改快照檔案。

### 5.2 什麼時候需要手動更新快照

只有在你**主動確認**「現在的行為就是我要保留的新基準」時，才手動執行對應的產生腳本，例如：

- 換了一版 YOLO 或 ST-GCN 模型
- 調整了 `SQAConfig` 或其他門檻值，預期行為本來就該不一樣
- 重構了 `process()`/`BehaviorTracker` 內部邏輯，肉眼確認過新輸出仍然合理

```powershell
# 更新 FrameProcessor characterization 快照
python paper/cat_monitoring_system/processors/tests/generate_frame_processor_snapshot.py

# 更新 BehaviorTracker 快照
python paper/cat_monitoring_system/trackers/tests/generate_behavior_tracker_snapshot.py

# 更新 Golden Dataset 快照（5 種行為）
python paper/cat_monitoring_system/processors/tests/generate_golden_dataset_snapshot.py
```

⚠️ **如果測試失敗，不要直接重跑產生腳本讓測試變綠**。應該先搞清楚「為什麼跑掉」，確認是上面列的那幾種預期中的改動，才手動更新快照——否則等於把可能的 bug 直接吃進基準裡，測試就永久失去偵測那個問題的能力了。

### 5.3 快照檔案放在哪裡

```
trackers/tests/snapshots/behavior_tracker_scripted_scenario.json
processors/tests/snapshots/frame_processor_process_characterization.json
processors/tests/snapshots/golden_dataset/{walk,lick,scratch,shake,stop}.json
```

這些檔案要跟程式碼一起進版控（git add），這樣其他人（或未來的你）才有基準可以比對。

## 六、常見狀況

### 6.1 測試被 SKIPPED，不是 PASSED/FAILED

`processors/tests` 裡的 Phase 1 測試需要真實的 YOLO/ST-GCN 模型檔跟固定測試影片存在才會執行，找不到就會顯示 `skipped`，不算失敗。在沒裝 cv2/torch/flask 的環境底下，所有需要這些套件才能 import 的測試檔也會直接整批 skip，不會報錯中斷（細節見 6.5）。

### 6.2 GPU 浮點數比對「差一點點」也算過

`confidence`/`class_probs` 這類 ST-GCN 推論輸出，用的是容許誤差比較（目前設定 `1e-4`），不是要求完全相等——不同硬體/驅動版本跑出來的浮點數本來就會有極小差異，這是正常現象，不算回歸。`behavior_id`/`is_still`/次數這類離散值才要求完全相等。

### 6.3 為什麼有 `pytest.ini`

`C:\ai_project\pytest.ini` 限定了裸執行 `pytest`（沒給路徑）時的預設掃描範圍，避免不小心掃到專案裡其他無關的腳本（例如 `cat_pose/` 底下一支檔名剛好符合測試命名規則、但其實會跳出互動視窗的手動除錯腳本）。明確指定路徑執行時不受這個限制。目前登記的資料夾：

```
paper/cat_monitoring_system/analytics/tests
paper/cat_monitoring_system/processors/tests
paper/cat_monitoring_system/trackers/tests
paper/cat_monitoring_system/server/tests
paper/cat_monitoring_system/utils/tests
paper/cat_monitoring_system/plugins/tests
paper/tests
```

### 6.4 測試會不會動到正式的 CSV/tracker 狀態檔？

不會。每個測試都用 `monkeypatch`／假時鐘把 `config.py::LoggingConfig`（或 `ModelPaths.OUTPUT_DIR` 等）的路徑導向暫時的測試資料夾，不會碰到正式的 `cat_monitoring_log.csv`、`behavior_segments_log.csv`、`tracker_state.json`、`ext_body_zones/results.csv`，也不會連上 Node-RED 或發送任何網路請求。

### 6.5 為什麼「明明是純函式」的模組也需要 yolo_new 環境才能收集

Python 的 import 是「整個模組檔案」層級的，不是「單一函式」層級的。以下幾種情況會讓一個本身零 GPU/cv2 邏輯的函式，還是需要對應套件才能被 pytest 收集：

- `server/routes.py` 檔案**開頭**就 `import cv2`、`from flask import ...`、`from processors.frame_processor import FrameProcessor`（間接需要 torch）——即使只是要測試檔案裡的 `_daily_record_from_dict()` 這種純函式，import 這支檔案本身就需要完整環境。
- `plugins/lick_stage/__init__.py` 會 `from plugins.lick_stage.manager import LickStagePlugin`，`manager.py` 又 `import` 了需要 cv2 的 `overlay.py`。所以只要 import `plugins.lick_stage.*` 底下**任何**子模組（包括完全沒有 cv2 邏輯的 `contact_regions.py`/`head_direction.py`/`ear_distance.py`，以及它的子套件 `ext_body_zones/regions.py`），都會觸發這條 import 鏈。

這些測試檔案開頭都有 `pytest.importorskip("cv2", reason="...")`，在沒裝 cv2 的環境會整份檔案安全跳過收集（顯示 skipped），不會報錯中斷其他測試。

### 6.6 API Regression Test 為什麼不怕碰到真的攝影機/GPU？

`server/tests/test_routes_api_regression.py` 建立獨立的 Flask app，並把 `server.routes` 模組層級的 `frame_processor`/`frame_streamer` 全域變數直接換成假物件（只實作路由邏輯實際會用到的屬性/方法），同時把 `_ensure_processor_started()` monkeypatch 成 no-op。這樣不管現在是不是在 `RunModeConfig` 的排程視窗內、有沒有接攝影機，測試行為都完全確定。
