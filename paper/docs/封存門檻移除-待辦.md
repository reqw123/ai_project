## 一、問題

Node-RED 封存一天到 `v2_daily_history` 時有一條門檻：**系統運行 ≥ 30 分鐘才寫進去**，不到就跳過（Debug 視窗出現「系統運行時間不足，跳過歷史記錄」）。

這條門檻是修正前遺留的規則（原本是「貓在畫面 ≥ 30 分鐘」，用意是不讓只開了兩分鐘的日子混進基線），2026-09-29 改分母定義時改成看系統運行時間，但沒有重新檢討它還需不需要存在。現在它已經**多餘**：

- **不會讓基線更正確**：能不能進基線由「個體化基線計算器」另外判斷——貓在畫面 ≥ 30 分鐘（時段模式 `MIN_PERIOD_SEC`）或 ≥ 1 小時（全天模式 `MIN_DAILY_SEC`）。貓在畫面 ≤ 系統運行，所以運行不到 30 分鐘的日子本來就過不了基線那一關。
- **看不到那一天**：被跳過的日子在歷史裡完全消失，分不出「沒開系統」還是「封存壞了」——驗證時要特地算運行時間夠不夠，才知道 Node-RED 該不該有那一天。
- **兩本日記不一致**：Python 的 `daily_history.db` 沒有這條門檻（只要存檔有累積任何時間就寫），同一天可能一邊有、一邊沒有。

## 二、改法

**只要那天系統有運行過（`run_seconds > 0`）就封存；要不要算進基線，全部交給基線計算器。**

- [x] **1. 改封存程式**：「每日統計彙整」與「跨日資料清除」兩個節點裡的共用封存段（一字不差各一份，改一邊要同步另一邊）
  - `const MIN_RECORD_SEC = 1800;` 與 `archiveDay()` 裡的判斷改成 `rec.run_seconds <= 0` 才跳過
  - 註解改寫：封存＝「那天有沒有開系統」，收錄＝基線計算器的貓在畫面門檻
  - 舊紀錄沒有 `run_seconds` 時 `buildRec()` 會退回 `total_uptime` 或「在畫面＋不在畫面」，不受影響
- [x] **2. 確認下游不會被短天數影響**
  - 「個體化基線計算器」：全天模式 `MIN_DAILY_SEC`、時段模式 `MIN_PERIOD_SEC` 會把短天數濾掉 → 不會進基線
  - 「判斷是否重算基線」：用 `v2_daily_history.length` 判斷「歷史夠不夠天數」→ 短天數會被算進「天數」，可能提早觸發重算、但算出來仍會因有效天數不足而回報資料不足；確認訊息是否需要改成「有效天數」
  - P4 面板：本來就依收錄門檻把未達標的日子標成無效（不計入基線），確認顯示正常
  - 歷史上限 90 筆：短天數也會佔名額，確認 90 筆仍夠用
  - `daily_history.csv`：短天數也會寫一列（固定欄位，不影響格式）
- [x] **3. 更新模擬測試**：`sim_midnight.js` 情境 E 目前預期「運行 < 30 分鐘不封存」→ 改成「會封存，但基線計算器不採用」；另加一個「運行 0 秒不封存」情境
- [x] **4. 部署**：repo `node-red-flows/cat_health_v4_flow.json` 與 `~/.node-red/flows.json` 必須完全相同（2026-09-29 部署時的做法：先備份，依節點 id 同步，比對每個節點完整內容一致、其他節點不動）
- [x] **5. 更新文件**：`分母定義與跨日封存-驗證待辦.md` 第一節第 3 列與第二節「9/29 可能不會出現在 Node-RED」的說明；`tools/verify_daily_archive.py` 若有提到 30 分鐘門檻一併改

## 三、補充：想「馬上看到」封存有沒有作用

正式封存在午夜，因為一天的數字要等當天結束才是最終版本。想立刻確認寫入功能，可以按 Node-RED「定時任務」分頁的 **「手動觸發每日彙整」**：會把今天目前的數字寫進 `v2_daily_history`；午夜時再以完整數字覆蓋同一天（依日期 upsert，不會重複）。
